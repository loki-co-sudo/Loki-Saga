## この記事について

TryHackMe の「Hashing Basics」というルームで学んだ内容を、Task 単位でまとめたノートです。Cyber Security 101 の「Cryptography」モジュールにあるルームで、ハッシュ関数（hash function）の性質と、その2大用途であるパスワード保管（password storage）と完全性チェック（integrity checking）を扱います。暗号入門の3部作（Cryptography Basics / Public Key Cryptography Basics / Hashing Basics）の3本目、最後のルームです。

課題の設問や答え、フラグはここには含めていません。各 Task で出てきた用語や考え方を、自分の理解として整理したものです。

このルームを進めていたころ、NIST が 2022 年 12 月に「SHA-1 を 2030 年末までに使用停止にすべき」という勧告を出していたことを知りました。SHA-1 は 2017 年に Google と CWI Amsterdam が現実的な衝突（異なる中身なのに同じハッシュになる 2 つの PDF）を作って見せた「SHAttered」以降、破られた関数として扱われています。このルームの Task 2 は、まさに「なぜ MD5 と SHA-1 をパスワードやデータの保護に使ってはいけないのか」を、衝突（collision）という概念から説明します。ふだん `apt update` の出力に出てくる `Hashes:` の行や、Linux の ISO をダウンロードしたあとに実行する `sha256sum` が何をしているのか、その意味を言葉にできるようになりました。

## Task 1: 導入

ハッシュ値（hash value）とハッシュ関数（hash function）とは何か、という導入です。ハッシュ関数は、任意の大きさの入力を受け取り、固定長の出力（ハッシュ値、ダイジェストとも呼びます）を返す関数です。同じ入力からは必ず同じ出力が出ます。

ルームの入口の例は「6 GB のファイルをダウンロードした。これが本物とビット単位で同じか、どう確かめるか」というものです。6 GB を丸ごと見比べる代わりに、両方のハッシュ値（たとえば 64 文字の文字列）を計算して比較すれば一瞬で済みます。一致すれば「まず間違いなく同一」と言えます。

**学んだこと**

ハッシュは「照合」のための道具だと最初に捉えると、後の Task がぶれずに読めました。暗号化（encryption）と違って鍵がなく、出力から入力に戻すこともできない、という枠組みを頭に置いておくと、Task 4 の「なぜパスワードを暗号化ではなくハッシュで保管するのか」や Task 8 の用語整理がすんなり入ります。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| hash function / hash value | 任意長の入力を固定長の出力に変換する関数と、その出力 |
| digest | ハッシュ値の別名。データを短く代表する「要約」 |
| integrity（完全性） | データが改ざん・破損していない状態。ハッシュ比較で確認できる |

## Task 2: ハッシュ関数

ハッシュ関数の性質を、実例で確認する Task です。

内容が 1 文字だけ違うファイル（`T` が入ったファイルと `U` が入ったファイル。この 2 文字は 2 進数で 1 ビットしか違いません）を用意して、`md5sum`・`sha1sum`・`sha256sum` で比較すると、出てくるハッシュはまったく似ていません。この「入力の小さな変化が出力を大きく変える」性質を、なだれ効果（avalanche effect）と呼びます。壊れたファイルや書き換えられたファイルを、ハッシュ比較で確実に弾けるのはこの性質のおかげです。

ハッシュ衝突（hash collision）は、異なる 2 つの入力が同じ出力になることです。出力は固定長なので種類は有限、入力は無限にあるため、衝突は数学的に必ず存在します（鳩の巣効果、pigeonhole effect）。良いハッシュ関数は、その衝突を「偶然にも意図的にも見つけにくい」ように作られています。MD5 と SHA-1 は、意図的に衝突を作る攻撃が実用化されたため、現在は安全でないとされます。

出力の読み方についてのメモ: `sha256sum` などは結果を 16 進数で表示します。16 進数 1 桁は 4 ビット、2 桁で 1 バイトなので、出力の文字数を数えて 2 で割ればバイト数が分かります。

**学んだこと**

「出力のバイト数 = 16 進の桁数 ÷ 2」という読み替えは、ハッシュ種別を推測するとき（Task 5）にそのまま使えます。衝突については、「必ず存在するが、良い関数なら遭遇確率が無視できる」という言い方が正確だと理解しました。MD5 と SHA-1 は個別には破られていても「両方を同時に衝突させる」攻撃はまだないため、両者を併記して改ざん検知に使う場面がある、という補足も知りました。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| avalanche effect | 入力 1 ビットの変化で出力が大きく変わる、良いハッシュ関数の設計目標 |
| hash collision | 異なる入力が同じハッシュになること。鳩の巣効果により不可避 |
| pigeonhole principle | n+1 個のものを n 個の箱に入れれば必ず 2 個入る箱ができる、という原理 |
| SHAttered | 2017 年に公表された SHA-1 の現実的な衝突攻撃 |
| md5sum / sha256sum | ファイルのハッシュ値を 16 進で表示する Linux コマンド |

## Task 3: 認証用パスワードの安全でない保管

パスワードを「やってはいけない方法」で保管した実例を 3 つ見る Task です。

- **平文（plaintext）保存**: そのまま保存する。データベースが漏れたら即座に全パスワードが露出します。クラッキングで定番の辞書ファイル `rockyou.txt` は、パスワードを平文で保存していた RockYou 社が漏洩したときの、約 1,400 万件の実パスワードそのものです。
- **非推奨の暗号化での保存**: Adobe の事例。ハッシュではなく可逆な暗号化を使い、さらにパスワードのヒントを平文で保存していたため、平文パスワードが比較的容易に復元されました。
- **弱いハッシュ + ソルトなし**: LinkedIn の 2012 年の事例。SHA-1 を使い、かつソルト（salt、ハッシュ前に加えるランダム値）を付けていませんでした。

パスワードマネージャー（password manager）はこの話とは別枠です。あちらは平文でパスワードを取り出せる必要があるためです。認証（authentication）は「利用者がパスワードを知っていること」を確認できればよいので、元に戻せないハッシュで足ります。

**学んだこと**

`rockyou.txt` を「便利な辞書」ではなく「実際の漏洩の落とし物」として捉えると、扱いの重みが変わりました。「認証には復元が要らない」という一点が、パスワードをハッシュで保管できる理由の核心だと整理できました。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| plaintext / cleartext | 暗号化もハッシュ化もされていない、そのままのデータ |
| rockyou.txt | RockYou 社の漏洩由来の実パスワード辞書。`/usr/share/wordlists/` にある |
| data breach（データ侵害） | 認可されていない者にデータが流出・アクセスされる事故 |
| salt / salting | ハッシュ前にパスワードへ加えるランダム値と、その付与 |
| deprecated（非推奨） | 古くなり使用が推奨されない技術・仕様 |

## Task 4: 安全なパスワード保管のためのハッシュ利用

では正しくはどうするか、という Task です。

パスワードそのものではなくハッシュ値を保存すれば、データベースが漏れても攻撃者は 1 件ずつクラックする必要があります。ただし、同じパスワードのユーザーは同じハッシュになるため、レインボーテーブル（rainbow table、ハッシュから平文への事前計算済みの対応表）で一気に逆引きされる恐れがあります。CrackStation のようなサイトは、この巨大な対応表を内部に持っています。

対策がソルトです。ユーザーごとに異なるランダム値をハッシュ前に連結すると、同じパスワードでもハッシュが変わり、事前計算した表が丸ごと無効になります。ソルトの目的は「事前計算をさせない」ことなので、データベースに平文で保存して構いません（秘密にする必要はありません）。

現代の推奨は、パスワード保管専用に設計されたハッシュ関数、具体的には Argon2・scrypt・bcrypt・PBKDF2 です。これらは意図的に計算が遅く、ソルトを内部で自動処理します。「では暗号化すればいいのでは」という疑問には、暗号化だと復号鍵を保存する必要があり、鍵が漏れれば全件復号されてしまう、という答えが返ってきます。

**学んだこと**

レインボーテーブルは「クラックにかかる時間を、ディスク容量と引き換えにする」手法だと理解しました。ソルトが公開値でよいのは、狙いが秘匿ではなく「表を作らせない」ことにあるからです。SHA-256 のような汎用で高速なハッシュを、そのままパスワードに使ってはいけない（速い = 総当たりされやすい）、という点が Task 6 につながります。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| rainbow table | ハッシュと平文の対応を事前計算した表。ソルトなしハッシュの逆引きに使う |
| bcrypt / scrypt / Argon2 / PBKDF2 | パスワード保管用に設計された、意図的に低速なハッシュ関数・鍵導出関数 |
| key derivation function（KDF） | パスワードから鍵やハッシュを導く関数。反復回数やメモリ量で総当たりを遅くする |
| CrackStation / Hashes.com | ハッシュから平文を逆引きするオンラインサービス |

## Task 5: パスワードハッシュを見分ける

攻撃側の視点で、手元のハッシュの種類をどう判断するか、という Task です。種類が分からないとクラックの方法を選べません。

Linux のパスワードハッシュは `/etc/shadow`（root だけが読める）に保存されています。昔は誰でも読める `/etc/passwd` にありました。ハッシュのフィールドは `$prefix$options$salt$hash` という形式で、先頭のプレフィックスがアルゴリズムを表します。

| プレフィックス | アルゴリズム |
| --- | --- |
| `$y$` | yescrypt（新しいシステムの既定・推奨） |
| `$7$` | scrypt |
| `$2a$` / `$2b$` / `$2y$` | bcrypt |
| `$6$` | sha512crypt |
| `$1$` | md5crypt |

Windows のパスワードは NTLM（MD4 の変種）でハッシュ化され、SAM（Security Accounts Manager）に保存されます。NTLM は MD5 と見た目が区別できないため、「どこで採取したか」という文脈で判断します。Web アプリのデータベースにあった 32 桁の 16 進数なら MD5 の可能性が高く、Windows の SAM から取り出したものなら NTLM、という具合です。

種類が絞れないときの調べ先が、hashcat 公式 wiki の「Example Hashes」ページです。各ハッシュ形式について、`hashcat -m` に渡すモード番号・分類・サンプルハッシュが一覧になっています。

**学んだこと**

プレフィックスのある Unix 形式は、`hashid` のような自動判定ツールが信頼できます。プレフィックスのない MD5・NTLM・LM は見た目が同じなので、ツールは候補を複数返すだけです。Example Hashes ページは `Ctrl+F` で名前の一部を検索し、同名が複数出るとき（`Cisco-IOS $8$` と `$9$` など）は設問が指定するプレフィックスで行を絞る、という使い方が定石でした。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| /etc/shadow / /etc/passwd | Linux のパスワードハッシュ格納ファイル（現行）と、かつての格納先 |
| crypt 形式（`$prefix$options$salt$hash`） | Unix パスワードハッシュの標準レイアウト |
| NTLM / SAM | Windows のパスワードハッシュ方式（MD4 派生）と、その格納データベース |
| hashID / name-that-hash | ハッシュ文字列から種別を推測するツール |
| Hashcat Example Hashes | 形式名・モード番号・サンプルの対応表。未知のハッシュ調査の出発点 |

## Task 6: パスワードクラッキング

hashcat を使って実際にハッシュをクラックする Task です。

パスワードハッシュは「復号」できません。暗号化されていないからです。クラックとは、候補パスワード（`rockyou.txt` など）を片端からハッシュし、ソルトがあれば加えて、ターゲットのハッシュと一致するものを探す作業です。GPU は単純な計算を大量に並列できるため、MD5 や SHA-256 のような汎用ハッシュのクラックが非常に速くなります。逆に bcrypt は GPU で高速化できないよう設計されており、それがクラック耐性になります。仮想マシンはホストの GPU を使えないので、本気でクラックするならホスト側で実行するのが基本です。

hashcat の基本構文は `hashcat -m <ハッシュ種別> -a <攻撃モード> <ハッシュファイル> <辞書>` です。`-m` は種別の番号（`0` = MD5、`3200` = bcrypt など）、`-a 0` は辞書を上から順に試すストレート攻撃です。

ここで私はつまずきました。1 問目のハッシュは `$2a$06$...` で始まっていたのに、`-m 0`（MD5）を指定して実行してしまい、

```
Token length exception
No hashes loaded.
```

で即座に止まりました。`$2a$` は Task 5 で見たとおり bcrypt のプレフィックスなので、正しくは `-m 3200` です。`Token length exception` は「`-m` で指定した種類と、実際のハッシュの形が合っていない」ときのエラーだと分かりました（MD5 は 32 桁の 16 進を期待しているのに、60 文字の bcrypt 文字列を渡したための不一致です）。

もう 1 つ気づいたのは、この Task の課題には「`rockyou.txt` のストレート攻撃だけでは解けないもの」が混ぜてあることです。その場合は、過去のクラック結果を蓄積したオンラインのデータベース（Hashes.com など）で引くか、`hashcat` にルール（`-r best64.rule` など。各辞書語に「先頭を大文字」「末尾に数字」といった変形を加える）を適用します。

**学んだこと**

手順としては「種類を判定 → `-m` を決める → 辞書で回す」の順で、Task 5 の見分けと Task 6 の実行は地続きでした。実務的には、まず既知ハッシュのデータベースに問い合わせるほうが速いことが多いですが、ペネトレーションテストでは顧客のハッシュを外部サイトに送ってよいかは交戦規定（Rules of Engagement）次第で、禁止ならローカルの `hashcat` 一択になります。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| hashcat | 高速なパスワードクラッカー。`-m` で種別、`-a` で攻撃モードを指定 |
| John the Ripper | もう一つの定番クラッカー。既定は CPU で、仮想マシンでもそのまま動く |
| dictionary attack / brute-force attack | 既知の候補を試す攻撃 / 全組み合わせを試す攻撃 |
| rule-based attack（`-r`） | 辞書の各単語に変形を加えて試す hashcat の攻撃手法 |
| Token length exception | 指定した `-m` と実際のハッシュ形式が食い違うときの hashcat のエラー |

## Task 7: 完全性チェックのためのハッシュ

ハッシュのもう 1 つの用途、ファイルの完全性チェックに戻る Task です。

配布元が「このファイルの SHA-256 は○○です」と公開しておき（Linux ディストリビューションの CHECKSUM ファイルなど）、ダウンロードした側は手元で `sha256sum` を実行して値が一致するか確認します。1 ビットでも壊れていれば、なだれ効果でハッシュが大きく変わるため、すぐ気づけます。同じハッシュのファイルは同じ内容なので、重複ファイルの検出にも使えます。

ただし、ファイルとハッシュの両方を書き換えられると気づけません。そのため本物の配布では、CHECKSUM ファイル自体に PGP 署名を付け、「この値リストは配布元が作ったもの」を保証します。ハッシュが完全性を、署名が真正性（authenticity）を担当する、という役割分担です。

HMAC（Keyed-Hash Message Authentication Code）は、ハッシュ関数と秘密鍵を組み合わせた仕組みです。鍵を知っている人だけが正しい HMAC を作れるので、「改ざんされていない（完全性）」に加えて「正しい送信者が作った（真正性）」まで一度に保証できます。式で書くと `HMAC(K, M) = H((K ⊕ opad) || H((K ⊕ ipad) || M))` で、鍵を 2 種類の定数と XOR して内側と外側で 2 回ハッシュする、という構造です。API リクエストの署名や JWT の `HS256` で実際に使われています。

**学んだこと**

ハッシュ単体では、改ざんの「検知」はできても「なりすまし」は防げない、という限界をはっきり理解しました。HMAC とデジタル署名はどちらも真正性を保証しますが、HMAC は送受信者が同じ秘密鍵を共有するのに対し、署名は公開鍵で誰でも検証できて否認防止にもなる、という違いがあります。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| checksum / integrity checking | 配布物のハッシュ値と手元の計算結果を比較する完全性確認 |
| `sha256sum -c` | チェックサムファイルを渡して一括検証するモード |
| HMAC | ハッシュ関数と秘密鍵による、完全性と真正性の検証コード |
| MAC vs digital signature | 共有秘密鍵を使う MAC と、公開鍵で検証できる署名の違い |
| JWT HS256 | JSON Web Token を HMAC-SHA256 で署名する方式 |

## Task 8: まとめ

ハッシュ・エンコード・暗号化の違いを整理する Task です。

| | 目的 | 鍵 | 元に戻せるか |
| --- | --- | --- | --- |
| ハッシュ（hashing） | 完全性・パスワード検証 | なし | 戻せない（一方向） |
| エンコード（encoding） | 形式変換・互換性 | なし | 戻せる（誰でも） |
| 暗号化（encryption） | 機密性 | あり | 戻せる（鍵があれば） |

エンコードは機密性を守りません。Base64（使う文字は `A–Z a–z 0–9 + /` と、末尾のパディング記号 `=`）は `base64 -d` で誰でもデコードできる、単なる形式変換です。バイナリを ASCII 文字だけで表してメール添付や JSON に埋め込むための仕組みで、暗号ではありません。ASCII や UTF-8 / UTF-16 / UTF-32 も「文字をバイト列でどう表すか」の話であって、暗号とは無関係です。

**学んだこと**

CTF で Base64 の文字列を見て「暗号化されている」と誤認しない、という判断基準ができました。末尾の `=` は Base64 を見分ける手がかりになります。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| encoding vs encryption | 互換性のための可逆変換（秘密を守らない）と、鍵で機密性を守る可逆変換 |

## おわりに

「Hashing Basics」は、「ハッシュは戻せない」という一点を軸にすると、パスワード保管も完全性チェックも同じ道具の別用途として一本につながりました。特に Task 5（ハッシュの見分け）と Task 6（クラッキング）は、`-m` を 1 つ間違えただけで `Token length exception` になるとおり、完全に地続きです。プレフィックスと採取場所から種類を当て、正しいモードを選んで hashcat を回す、という流れを一度自分の手で通せたのは大きな収穫でした。

余談ですが、このルームで既定・推奨として出てくる yescrypt（`$y$`）は、Debian 11 以降の Linux で新しいパスワードのハッシュ方式の既定になっています。手元の `/etc/shadow` を見て `$y$` で始まっていたら、それがこのルームで学んだ「現代の Unix パスワードハッシュ」です。これで暗号入門 3 部作は完走です。次は、この Task 6 で触れたクラッキングを本格的に扱う「John the Ripper」のルームに進みます。
