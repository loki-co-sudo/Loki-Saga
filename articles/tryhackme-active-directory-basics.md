## この記事について

TryHackMeの「Active Directory Basics」というルームで学んだ内容を、Task単位でまとめたノートです。Windows Fundamentals 1〜3に続く「Windows and AD Fundamentals」モジュールの1本で、企業ネットワークの管理を支えるActive Directory(AD)の基本構成要素――ユーザー・マシン・セキュリティグループ・OU・グループポリシー(GPO)・認証プロトコル(Kerberos / NetNTLM)・ツリー/フォレスト/信頼関係――を、架空の会社「THM Inc.」のIT管理者という設定で一通り扱っています。

課題の設問や答え(flag)はここには含めていません。あくまで各Taskで学んだ考え方・仕組みを、自分の理解として整理したものです。

## Task 1〜2: Active Directoryが必要になる理由

パソコンが数台の会社なら、1台ずつ手作業でユーザーを作って設定しても問題は起きません。でも会社が成長して端末やユーザーが数百人規模になると、1台ずつの個別管理はどう考えても破綻します。

Active Directory(AD)は、この「規模が大きくなったときの管理」を解決するための仕組みです。ユーザーやコンピューターの情報を「ドメイン」という単位でまとめ、Active Directoryという中央のリポジトリに集約します。このサービスを実際に動かしているサーバーがドメインコントローラー(Domain Controller、DC)です。学校や大学で、どの端末からでも同じIDでログインできたり、勝手に管理者権限の設定を変えられなかったりするのも、裏側でADが動いているからだと知り、身近な例で腑に落ちました。

**学んだこと**

「一元化されたアイデンティティ管理」と「一元化されたセキュリティポリシー管理」という2つのメリットが、AD導入の本質的な動機だとわかりました。この後のTaskで出てくるOUやGPOも、突き詰めればこの2つを実現するための道具立てです。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| Active Directory (AD) | ユーザー・コンピューターなどの情報を一元管理するディレクトリサービス |
| Windows domain | ある組織の管理下に置かれたユーザーとコンピューターの集合 |
| Domain Controller (DC) | Active Directoryのサービスを実行するサーバー |

## Task 3: ADに登録される「オブジェクト」たち

ADの中核はAD DS(Active Directory Domain Service)で、ネットワーク上のあらゆる「オブジェクト」の情報を持つカタログのような役割を果たします。代表的なオブジェクトはユーザー・マシン・セキュリティグループの3種類です。

ユーザーは人だけでなく、IISやMSSQLのようなサービスを動かすための「サービス用ユーザー」も含みます。マシンもドメイン参加時に自動でアカウントが作られ、名前の末尾に`$`が付く命名規則(例: `DC01$`)を持ちます。パスワードは120文字のランダム文字列で自動ローテーションされるため、人間が推測してログインすることは事実上不可能です。

セキュリティグループは「リソースへの権限をまとめて付与するための入れ物」で、Domain Adminsのようにドメイン全体を管理できる強力なグループも存在します。これらはすべて「セキュリティプリンシパル(security principal)」と呼ばれ、ADによって認証され、権限を割り当てられる対象という共通点があります。

**学んだこと**

このTaskで一番腹落ちしたのは、OU(Organizational Unit、組織単位)とセキュリティグループの役割の違いです。OUは「ポリシーを適用するための入れ物」で1人1つしか所属できないのに対し、セキュリティグループは「権限を付与するための入れ物」で複数所属が可能。似たもの同士に見えて、目的が全然違うという整理は覚えておきたいと思いました。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| security principal | ADに認証され権限を割り当てられるオブジェクト全般(ユーザー/マシン/グループ) |
| machine account | ドメイン参加PCごとに自動生成されるアカウント。名前は`コンピューター名$` |
| Organizational Unit (OU) | ポリシー適用のための分類単位。1ユーザーにつき1つのみ所属可能 |
| Domain Admins | ドメイン全体を管理できる最上位の管理者グループ |

## Task 4: ユーザー管理と委任(Delegation)

このTaskでは実際にAD管理者として手を動かし、組織図に合わせてOUやユーザーを整理する作業を体験しました。特に面白かったのが「委任(delegation)」という仕組みです。

ドメイン全体を管理できるDomain Adminは強力すぎて、パスワードリセットのような細かい作業のたびに呼び出すのは非効率です。そこで「特定のOUに対して、特定の操作だけ」を一般ユーザーに委任できる機能がADには用意されています。今回はIT担当者役のユーザーに、ある部門のパスワードリセット権限だけを委任する、という最小権限の原則(Principle of Least Privilege)を体感する演習でした。

委任されたユーザーは「Active Directory Users and Computers」というGUI管理ツールを開く権限までは持っていないため、PowerShellのコマンドレット(`Set-ADAccountPassword`など)を使って操作する、という点も実務的で参考になりました。

**学んだこと**

ラボ環境へのRDP(リモートデスクトップ)接続で地味にハマったのが、ドメインアカウントの指定方法でした。ユーザー名を`ドメイン\ユーザー名`のようにバックスラッシュで直接つなげると、クライアントがKerberos認証を自動で試みて「KDCが見つからない」というエラーになることがあります。ドメイン指定を別オプションに分離するとこの問題を回避できました。もう1つ、「次回ログイン時にパスワード変更を必須にする」設定をした状態だと、RDPのNLA(Network Level Authentication、デスクトップ表示前の事前認証)の段階でパスワード変更フローがうまく処理できず接続に失敗するケースがある、というのも実際にやってみて初めて知った制約でした。教科書通りに進まない部分にこそ学びがあるな、と感じたTaskです。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| Delegate Control | OUに対する特定の権限をユーザーに委任するADの機能 |
| Principle of Least Privilege(最小権限の原則) | 必要最小限の権限だけを付与するセキュリティの基本原則 |
| Set-ADAccountPassword | PowerShellでADユーザーのパスワードをリセットするコマンドレット |
| NLA (Network Level Authentication) | RDP接続時にデスクトップ表示前に行われる事前認証 |

## Task 5: マシンの整理(Workstations / Servers / DC)

ドメインに参加したマシンは、デフォルトですべて「Computers」という1つのコンテナに入ってしまいます。でもワークステーション(一般ユーザーの端末)・サーバー・ドメインコントローラーでは求められるセキュリティレベルがまったく違うため、それぞれ別のOUに分けて管理するのが定石だと学びました。

特にドメインコントローラーは、全ユーザーのハッシュ化されたパスワードを保持しているため、乗っ取られた場合の被害が最も大きい、ネットワーク上で最重要な防衛ラインです。

**学んだこと**

「ワークステーションには権限の高いユーザーを絶対にログインさせてはいけない」というルールが特に印象的でした。もし普段使いのPCに管理者アカウントでログインする習慣があると、そのPCが乗っ取られた瞬間にドメイン全体が危険にさらされてしまいます。マシンの分類は、単なる整理整頓ではなく実効的なセキュリティ対策なのだと理解しました。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| Workstation | 一般ユーザーが日常業務に使う端末 |
| privileged user | 管理者権限など高い権限を持つユーザー |
| hashed password(ハッシュ化パスワード) | パスワードを不可逆な形式に変換した値 |

## Task 6: グループポリシー(GPO)

OUに分けてきた本当の目的は、OUごとに異なるポリシーを配布できるようにすることです。Windowsではこれをグループポリシーオブジェクト(GPO)という単位で管理します。GPOを作成し、適用したいOUに「リンク」して初めて効果が発生する、という流れがポイントでした。

GPOにはComputer Configuration(コンピューター向け)とUser Configuration(ユーザー向け)の2種類の設定があり、親OU(ドメインルートを含む)にリンクしたGPOは子OUにも継承される、という性質も学びました。今回は「IT部門以外はコントロールパネルにアクセスできないようにする」「操作がない状態が5分続いたら画面を自動ロックする」という2つの実践的なGPOを作成する演習でした。

**学んだこと**

GPOの実体はSYSVOLというDC上のネットワーク共有に置かれていて、各マシンが定期的にそこを見に行って同期する、という配布の仕組みが面白かったです。変更の反映には最大2時間かかることがありますが、`gpupdate /force`コマンドで即座に強制同期できる、というのは実務でもよく使われる小技として覚えておきたいと思いました。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| Group Policy Object (GPO) | OUに適用する設定の集合体 |
| policy inheritance(ポリシーの継承) | 親OUに適用したGPOが子OU全体に伝わる性質 |
| SYSVOL | GPOなどをDCから各マシンへ配布するためのネットワーク共有 |
| gpupdate /force | GPOの適用を即座に強制するコマンド |

## Task 7: 認証方式(Kerberos / NetNTLM)

Windowsドメインの認証には、現在標準のKerberosと、互換性維持のために残されているレガシーなNetNTLMの2つのプロトコルがあります。

Kerberosはチケットベースの仕組みで、まずKDC(Key Distribution Center、鍵配布センター。通常DC上で動作)からTGT(Ticket Granting Ticket)という「これからチケットをもらうためのチケット」を受け取り、個別のサービスを使いたいときにTGTを使ってTGS(Ticket Granting Service)という専用チケットを発行してもらう、という2段階の仕組みになっています。一方NetNTLMは、サーバーが出す「チャレンジ」に対してパスワードハッシュを使った「レスポンス」を返せるかどうかで本人確認をする、チャレンジ・レスポンス方式です。

**学んだこと**

TGT・TGS・krbtgt・SPNといった単語は、この先「AD攻撃手法」を学ぶ際にも頻出する基礎用語だと知り、ここでざっくりでも仕組みを掴んでおく価値を感じました。またNetNTLMも含め、パスワードそのものやそのハッシュがネットワーク上を直接流れることはない、というセキュリティ設計の考え方も勉強になりました。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| Kerberos | チケットベースのWindowsドメイン標準認証プロトコル |
| KDC (Key Distribution Center) | Kerberosチケットを発行するサービス。通常DC上で稼働 |
| TGT / TGS (Ticket Granting Ticket / Service) | チケットを要求するための最初のチケットと、個別サービス用のチケット |
| NetNTLM | チャレンジ・レスポンス方式のレガシー認証プロトコル |

## Task 8: Tree・Forest・Trust Relationship

1つの会社=1つのドメインという話が、企業の成長とともにどう拡張していくかを学ぶTaskでした。同じ名前空間(namespace)を共有する複数ドメインの集まりを「Tree(ツリー)」、異なる名前空間を持つ複数のツリーの集まりを「Forest(フォレスト)」と呼びます。例えば海外拠点ごとにサブドメインを分けたり、企業買収で別会社のドメインを統合したりする際にこの構造が使われます。

拠点やドメインをまたいでリソースにアクセスする必要が出てきた場合は、「信頼関係(Trust Relationship)」でドメイン同士を結び付けます。ここで面白いのが、信頼の向きとアクセスの向きが逆になるという点です。「AがBを信頼する」というのは「Bのユーザーがアクセスできるようになる可能性がある」という意味で、直感と逆なので少し混乱しました。

**学んだこと**

範囲が広がるほど、より強い権限を持つグループが登場する、という構造も整理できました。単一ドメインを管理するDomain Adminsに対し、フォレスト全体を管理できるEnterprise Adminsという、より広い権限を持つグループが存在します。「管理の独立性」と「アクセスの連携」は別物として設計されている、という視点はAD全体を理解するうえで大事なポイントだと感じました。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| Tree | 同一名前空間を共有する複数ドメインの階層構造 |
| Forest | 異なる名前空間を持つ複数Treeの集合 |
| Trust Relationship | ドメイン間でユーザーの認可を可能にする関係。one-way / two-wayがある |
| Enterprise Admins | フォレスト全体に管理者権限を持つセキュリティグループ |

## Task 9: まとめ

このルームでは、AD の基本的な部品(ユーザー・マシン・グループ・OU)、管理の仕組み(GPO・委任)、認証の仕組み(Kerberos・NetNTLM)、そして大規模組織向けの構造(Tree・Forest・Trust)まで、ADの骨格をひと通り学びました。

あくまで入門編という位置づけで、TryHackMe側では、ADを守る側の視点を学ぶ「Active Directory Hardening」と、攻める側の視点で設定ミスを悪用する手法を学ぶ「Compromising Active Directory」という、2つの発展的なルーム/モジュールが案内されていました。

**学んだこと**

セキュリティを学んでいく上でこの先「攻撃側」の視点に進むことが多くなりそうですが、今回学んだOU・GPO・Kerberosの基礎知識がなければ、そもそも「何が悪用されているのか」を理解できません。地味に見える基礎ほど後から効いてくる、というのを実感したルームでした。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| Active Directory Hardening | ADのセキュリティを固める防御視点のTryHackMeルーム |
| Compromising Active Directory | ADの設定ミスを悪用する攻撃手法を学ぶTryHackMeモジュール |
