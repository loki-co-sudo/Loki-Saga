## この記事について

TryHackMe の「John the Ripper: The Basics」というルームで学んだ内容を、Task 単位でまとめたノートです。Cyber Security 101 の「Cryptography」モジュールにあり、暗号入門の 3 ルーム（Cryptography Basics / Public Key Cryptography Basics / Hashing Basics）の続きに置かれた、初めての本格的な実技ルームでした。

扱うのは John the Ripper（以下 John）という、ハッシュやパスワード付きファイルに対して辞書攻撃（dictionary attack）を高速にかけるツールです。Windows の認証ハッシュ、Linux の `/etc/shadow`、パスワード付きの Zip / RAR、SSH の秘密鍵と、対象を変えながら同じ道具を使い回す構成になっています。

課題の設問・答え・フラグはここには含めていません。各 Task で出てきた用語や、手を動かして分かったことを、自分の理解として整理したものです。

このルームで最初にダウンロードして使うワードリストが `rockyou.txt` です。2009 年に RockYou というソーシャルアプリ企業がデータ侵害を受け、約 3,200 万件のアカウントのパスワードが流出しました。しかもハッシュ化されておらず平文で保管されていたため、流出物がそのまま「人間が実際に付けたパスワードの一覧」になってしまいました。それから 15 年以上経った今も、このリストは弱いパスワードのクラックによく効きます。「人はそう簡単にパスワードの付け方を変えない」という事実を、道具を通して確認していく 60 分でした。

## Task 1: 導入

John が何をするツールなのか、という導入です。パスワードは普通、ハッシュ関数を通した「ハッシュ値」の形で保管されます。ハッシュは一方向関数（one-way function）なので、ハッシュ値から元のパスワードを計算で戻すことはできません。

ただし「戻せない」ことと「クラックできない」ことは別です。候補になる単語を大量に用意し、同じハッシュ関数にかけて、出てきたハッシュ値が狙いのものと一致するか総当たりで比べる。一致すれば元の単語が分かります。これが辞書攻撃で、John はこれを非常に速く回してくれる道具です。

このルームで使うのは素の John ではなく、「Jumbo John」というコミュニティ拡張版です。対応するハッシュ形式が多く、後半で使う変換ツール（`zip2john` など）も同梱されています。

**学んだこと**

「ハッシュは逆算できないが、作って照合することはできる」という枠組みを最初に押さえると、以降の Task がぶれずに読めました。John がやっているのは魔法ではなく、「候補を片っ端からハッシュ化して突き合わせる」という素朴な作業の高速化です。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| John the Ripper | 多数のハッシュ形式に対応したパスワードクラッキングツール |
| Jumbo John | 対応形式と付属ツールを増やしたコミュニティ拡張版。このルームの前提 |
| dictionary attack | 候補語リストを順にハッシュ化して照合する攻撃手法 |
| one-way function | 順方向の計算は容易、逆方向は事実上不可能な関数 |

## Task 2: 基本用語

ハッシュ、ハッシュアルゴリズム（MD4 / MD5 / SHA1 / NTLM）、一方向性といった用語のおさらいです。「なぜ逆算が難しいのか」を、計算複雑性理論の P と NP の話に軽く触れながら説明しています。ハッシュを計算するアルゴリズムは現実的な時間で解ける側（P）、逆算は現実的な時間で解けない側、というイメージです。この節は「面白いが本題ではない」と割り切って読みました。

**学んだこと**

MD5 は 16 進 32 文字、SHA1 は 40 文字、というように「出力の長さ」がハッシュ種別の当たりをつける手がかりになります。ただし同じ長さの別形式（MD5 と NTLM など）もあるので、長さだけで決めず識別ツールと実行結果で確認する、という進め方を意識しました。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| MD5 / SHA1 | 旧世代のハッシュアルゴリズム。衝突が実証されており現在は非推奨 |
| NTLM (NThash) | 現代の Windows がパスワードを保管する形式。MD5 と長さが同じ |
| P vs NP | 計算複雑性理論の未解決問題。「検証は速いが求解は速いとは限らない」 |

## Task 3: 環境のセットアップ

Jumbo John とワードリストを用意する Task です。攻撃用の Linux 環境（TryHackMe の AttackBox や Kali）には Jumbo John が最初から入っています。`john` と打って 1 行目に `jumbo` の文字が見えれば大丈夫です。

私はローカルの Kali で進めました。`john` 本体に加えて `zip2john` / `rar2john` / `ssh2john` / `unshadow` がすべて `PATH` 上にあることを確認しました。

ワードリスト `rockyou.txt` は、Kali では圧縮されたまま `/usr/share/wordlists/rockyou.txt.gz` に置かれていることがあります。その場合は展開が必要です。私の環境では `.gz` を残したまま同じ場所に展開しておきました（ルームのコマンド例が `/usr/share/wordlists/rockyou.txt` を前提にしているので、標準の場所に置いておくと後がラクです）。展開後のサイズは約 133 MB、行数はおよそ 1,434 万でした。

**学んだこと**

素の John（core 版）には `zip2john` などの変換ツールが含まれず、後半の Task が進められません。「必ず Jumbo 版を使う」というのがこのルーム全体の前提でした。ワードリストの置き場所（`/usr/share/wordlists`）と、圧縮されている場合の展開手順も、地味ですが毎回引っかかるところなので手を動かして覚えました。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| rockyou.txt | 2009 年の RockYou 社データ侵害由来のパスワードリスト。約 1,434 万件 |
| /usr/share/wordlists | Kali / AttackBox でワードリストが置かれる標準ディレクトリ |
| gunzip -k | gzip ファイルを展開しつつ元の `.gz` を残すオプション |

## Task 4: 基本的なハッシュのクラック

このルームで一番よく打つコマンドの形が出そろう Task です。基本構文は `john [オプション] [ファイル]` で、よく使うのは次の 2 つです。

- `john --wordlist=<ワードリスト> <ファイル>` … 形式を John に推測させる自動クラック
- `john --format=<形式> --wordlist=<ワードリスト> <ファイル>` … 形式を明示してクラック

形式が分からないときは、先にハッシュ種別を調べます。ルームでは `hash-identifier`（`hash-id.py`）という Python ツールを使いますが、Kali には `hashid` というコマンドも入っています。`hashid -mj <ハッシュ>` とすると、候補の種別に加えて John の形式名（`raw-md5` など）まで表示してくれるので、そのまま `--format=` に貼れて便利でした。

素朴なハッシュ（ソルトなしのダイジェスト）を John に渡すときは、形式名の頭に `raw-` を付けることが多いです（`raw-md5`、`raw-sha1` など）。付けるべきか迷ったら `john --list=formats` で正式名を確認できます。

**学んだこと**

クラックに成功すると、John は結果を `~/.john/john.pot` に記録します。同じコマンドをもう一度打つと「No password hashes left to crack」と出ますが、これはエラーではなく「もう解けている」という意味です。結果を見返すときは `john --show` を使う、という運用を最初に知っておくと戸惑いません。

初回の実行で出た `Warning: no OpenMP support for this hash type, consider --fork=16` も、エラーではなく「並列化したければ `--fork` を使うと速いですよ」という提案でした。処理が一瞬で終わる軽いハッシュなら無視して問題ありません。John の出力は、警告や案内がエラーのような見た目で並ぶので、1 行ずつ意味を確かめる癖をつけました。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| hashid / hash-identifier | 入力ハッシュの種別候補を推定するツール。`--format=` 選定の助けになる |
| raw- プレフィックス | John で「ソルトなしの標準ハッシュ」を指すときの接頭辞 |
| john.pot | クラック結果を保存するファイル（既定は `~/.john/john.pot`） |
| john --show | クラック済みの結果を再表示するオプション |

## Task 5: Windows 認証ハッシュのクラック

Windows がユーザーやサービスのパスワードを保管する形式が NTLM（NThash）です。John の形式名は `nt` です。16 進 32 文字で MD5 とまったく同じ長さなので、ここは長さではなく文脈（「Windows の認証ハッシュ」）で判断します。

NTLM ハッシュは、Windows のローカルアカウント情報を保管する SAM データベースや、Active Directory の `NTDS.dit` から取り出せます。ただしそこにアクセスするには、たいてい先に特権昇格（privilege escalation）が必要です。また、クラックしなくても NTLM ハッシュをそのまま認証に使い回す「pass the hash」という攻撃があるため、実務では「クラックは平文パスワードそのものが欲しいときの手段」という位置づけになります。

**学んだこと**

同じ「16 進 32 文字」でも、MD5 なのか NTLM なのかは長さで区別できません。ここで Task 2 の「長さは手がかりだが決め手ではない」が効いてきました。攻撃の流れ全体（ハッシュを取るには特権が要る、取れても pass the hash という別ルートがある）の中でクラックがどこに位置するのかを整理できたのが収穫でした。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| NTLM (NThash) | Windows のパスワードハッシュ形式。John の形式名は `nt` |
| SAM / NTDS.dit | Windows のパスワードハッシュの保管場所（ローカル / ドメイン） |
| pass the hash | ハッシュを平文化せず認証に使い回す横展開の手法 |
| privilege escalation（特権昇格） | 一般権限から管理者・SYSTEM 権限へ格上げすること |

## Task 6: /etc/shadow のハッシュのクラック

Linux のパスワードハッシュは `/etc/shadow` に保管されます。このファイルは root しか読めません。一方、ユーザー名や UID などの一般情報は誰でも読める `/etc/passwd` にあり、ハッシュがあった場所には `x` という目印だけが残っています。昔は `/etc/passwd` にハッシュも入っていたのですが、「誰でも読めるファイルに全員のハッシュがある」のは危険なので、ハッシュだけを `/etc/shadow` に移した、という経緯です。

John は、シャドウ化される前の「1 行にすべて入っていた形式」を入力として期待します。そこで `unshadow` という付属ツールで、`/etc/passwd` 側の情報と `/etc/shadow` 側のハッシュをユーザーごとに 1 行にまとめてから John に渡します。

`/etc/shadow` のハッシュ欄の先頭 `$6$` は「これは sha512crypt」という印です（`$1$` は MD5crypt、`$5$` は SHA-256crypt、`$2y$` は bcrypt）。`$6$` と次の `$` に挟まれた文字列がソルト（salt）です。sha512crypt はソルト付きで、しかも内部でハッシュ計算を何千回も繰り返す（ストレッチング）ため、MD5 や NTLM と比べて桁違いに遅いです。ここで初めて「待つ」時間が発生しました。`--fork` で CPU コアに分けると多少速くなります。

なお、配布ファイルの名前がルーム本文では `etchashes.txt` と書かれていますが、実際にダウンロードされるファイル名は `etc_hashes.txt`（アンダースコアあり）でした。細かいですが、コマンドを打つときに一度つまずきました。

**学んだこと**

「なぜ 2 ファイルに分かれているのか」を理解すると、`unshadow` が何をしているのかが腑に落ちます。`/etc/passwd` が全員に読めるのは、名前と ID 番号の対応表として多くのプログラムが参照するからで、そこにハッシュを置きっぱなしにするわけにいかない。だからハッシュだけ隔離した、という話です。ソルトとストレッチングが「クラックを遅くするための仕組み」だと、実行時間の差として体感できました。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| /etc/shadow / /etc/passwd | Linux のパスワードハッシュの保管場所と、一般情報の保管場所 |
| unshadow | passwd と shadow を結合して John 用の入力を作る付属ツール |
| sha512crypt（`$6$`） | 現代の多くの Linux が既定で使うパスワードハッシュ方式 |
| salt / stretching | ソルトは事前計算攻撃を防ぐランダム値、ストレッチングは計算を意図的に重くする繰り返し |

## Task 7: シングルクラックモード

ここが個人的に一番つまずいた Task です。

`--single`（シングルクラックモード）は、外部のワードリストではなく、**ユーザー名などの手がかりから候補をその場で作って試す**モードです。人は `Markus1`、`Markus!`、`MArkus` のように「名前＋ちょい足し」でパスワードを作りがちで、John はこの「大文字化・数字付け・記号付け」を規則（mangling rules）に従って自動生成します。

このモードでは、入力ファイルを `ユーザー名:ハッシュ` の形にしておく必要があります。ハッシュだけだと、John には変形の材料になるユーザー名が見えません。

私は最初この前処理を忘れて、ハッシュだけのファイルに `--single` をかけました。結果は数秒で `0g 0:00:00:00 DONE ... 0p/s 0c/s`。1 件もクラックできず即終了です。エラーメッセージは出ません。おかしいと思って統計をよく見ると、候補生成レートを表す `p/s` が 0 でした。試した候補が 0 件、つまり John は何もせずに終わっていたわけです。ファイルの行頭にユーザー名を付け直したら、今度はちゃんと候補が回り始めました。

「エラーは出ないが結果も出ない」ときは、`p/s`（1 秒あたりの候補数）を見る。この読み方を、身をもって覚えました。

**学んだこと**

シングルクラックモードは、Task 8 のカスタムルールと地続きです。「単語を変形して候補を増やす」という発想は同じで、Task 7 は John があらかじめ持っている変形規則を使い、Task 8 は自分で規則を書く、という違いです。また、`/etc/passwd` の GECOS フィールド（氏名や電話番号などのメモ欄）も John は候補の材料に使います。「その人にまつわる文字列はすべてパスワード候補になりうる」という考え方は、防御側で「名前や誕生日を含むパスワードを禁止する」対策の理由そのものでした。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| single crack mode (`--single`) | ユーザー名などから候補を動的生成するモード。入力は `username:hash` 形式 |
| word mangling / mangling rules | 単語を大文字化・数字付けなどで変形して候補を膨らませる仕組み |
| GECOS field | `/etc/passwd` の第 5 フィールド。氏名・連絡先などのメモ欄 |
| p/s（candidates per second） | 候補生成レート。0 なら「試すものが無い」状態のサイン |

## Task 8: カスタムルール

Task 7 の変形を、自分で規則を書いて行う Task です。

多くの組織は「大文字・小文字・数字・記号を各 1 つ以上」というパスワード複雑性（password complexity）を課します。すると利用者は `Polopassword1!` のように「先頭を大文字にして、末尾に数字、最後に記号」という、覚えやすく似通った形に落ち着きます。攻撃側はこの「追加要素が来る位置」が読めるので、素の単語に決まった飾りを付ける規則を書けば、複雑性を満たした弱いパスワードを効率よく試せます。

規則は `john.conf` に `[List.Rules:名前]` というセクションで書き、`--rule=名前` で呼び出します。主な修飾子は `A0`（先頭に追加）、`Az`（末尾に追加）、`c`（大文字化）で、追加する文字は `[0-9]` や `[A-Z]`、`[!£$%@]` のように文字集合で指定します。たとえば `cAz"[0-9] [!£$%@]"` は「先頭大文字 → 末尾に数字 → さらに末尾に記号」で、`Polopassword1!` の形を作ります。

設定ファイルを編集するので、事前に `john.conf` のバックアップを取ってから作業しました。

**学んだこと**

これは攻撃テクニックであると同時に、防御側への示唆でもあります。「複雑性ルールを課しても、人間の癖（大文字は先頭、数字と記号は末尾）まで見れば予測できる」というのが要点で、近年のパスワードガイドラインが「複雑性の強制よりも長さと使い回しの排除を重視する」方向に動いている理由が、手を動かして納得できました。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| custom rules (`[List.Rules:名前]`) | `john.conf` に書く自作の変形規則。`--rule=名前` で呼ぶ |
| 修飾子 `A0` / `Az` / `c` | それぞれ先頭追加・末尾追加・大文字化 |
| password complexity policy | 文字種の混在などを強制する規則。人間の癖で逆に予測可能になる |

## Task 9 / Task 10: パスワード付き Zip / RAR

構造は Task 6 とまったく同じで、「変換ツールでハッシュ形式に落とす → John にかける」の 2 段構えです。

- Zip: `zip2john <ファイル.zip> > <出力ファイル>` → `john --wordlist=<ワードリスト> <出力ファイル>`
- RAR: `rar2john <ファイル.rar> > <出力ファイル>` → 同様

`>` はリダイレクトで、コマンドの出力を画面ではなくファイルに書き込む記号です。変換後の入力はすでに John 用に整形されているので、`--format=` は基本的に不要でした。クラックに成功したら、そのパスワードで `unzip` / `unrar x`（または `7z x`）を実行して中身を取り出します。

**学んだこと**

`unshadow` / `zip2john` / `rar2john` と、対象は違っても「John が読める形に変換する前処理」という役割は同じでした。ここまで来ると、次の Task で何が出てきても「まず変換ツールを探す」という当たりが付くようになります。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| zip2john / rar2john | パスワード付き書庫から John 用ハッシュを抽出する付属ツール |
| リダイレクト `>` | コマンド出力をファイルへ保存するシェルの記法 |
| unzip / unrar / 7z | 書庫を展開するコマンド。クラック後に中身を取り出すのに使う |

## Task 11: SSH 秘密鍵のクラック

対象が SSH の秘密鍵ファイル `id_rsa` になっただけで、やはり同じパターンです。`ssh2john id_rsa > <出力ファイル>` で変換し、`john --wordlist=<ワードリスト> <出力ファイル>` にかけます。`ssh2john` が単体コマンドとして無い環境では、`python3 /usr/share/john/ssh2john.py` のようにスクリプトを直接実行します。

前提として、SSH には「パスワード認証」と「公開鍵認証」があり、公開鍵認証では手元の秘密鍵 `id_rsa` を使ってログインします。この秘密鍵ファイル自体がパスフレーズ（passphrase）で暗号化されていることが多く、CTF では「鍵は手に入れたがパスフレーズが分からない」場面がよくあります。そこを John で解く、という位置づけです。

**学んだこと**

パスフレーズが分かったあと、実際に鍵を使うには `chmod 600 id_rsa` でパーミッションを絞る必要があります。これを忘れると SSH が「鍵が他人にも読める状態だ」と判断してログインを拒否します。クラックそのものより、この後始末で一度止まりました。「鍵ファイル入手 → パスフレーズをクラック → SSH ログイン」という流れは、CTF の定番ルートとして頭に入れておこうと思います。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| ssh2john | SSH 秘密鍵を John 用ハッシュへ変換するスクリプト |

## Task 12: まとめ

ルーム全体のまとめと、Openwall Wiki など次に読む資料の案内です。

このルームを 1 文にすると、「対象を `*2john` 系のツールでハッシュ形式に変換し、`john --wordlist=rockyou.txt` に（必要なら `--format=` や `--rule=`、`--single` を足して）かける」に尽きます。`/etc/shadow` も Zip も RAR も SSH 鍵も、入口が違うだけで通り道は同じでした。

**学んだこと**

道具の使い方そのものより、「同じ型を対象を変えて何度も適用する」という設計に気づけたのが大きかったです。次に未知のハッシュや暗号化ファイルに出会っても、「John に対応形式はあるか」「変換ツールはあるか」をまず調べる、という手順が体になじみました。GPU を使う `hashcat` も役割が近いので、次はそちらの「モード番号で形式を指定する」やり方と比べてみたいと思います。
