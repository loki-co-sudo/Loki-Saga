## この記事について

TryHackMe の「Moniker Link (CVE-2024-21413)」というルームで学んだ内容を、Task 単位でまとめたノートです。Cyber Security 101 の「Exploitation Basics」モジュールにあるルームで、2024年2月に公表された Microsoft Outlook の脆弱性を題材に、脆弱性の仕組み・実際の悪用・検知・対策までを一通り扱います。

課題の設問や答え、フラグはここには含めていません。また、このルームは攻撃を実演するタイプですが、この記事では再現手順そのものは書かず、「なぜその攻撃が成立するのか」という考え方の整理にとどめています。

ソフトウェアの脆弱性というと、複雑なメモリ破壊やチェーンした条件を思い浮かべがちです。ですが今回の CVE-2024-21413 は、悪意あるリンクの中に感嘆符(`!`)を1つ混ぜるだけで Outlook のセキュリティ機構を回避できてしまう、という拍子抜けするほど単純なものでした。CVSS スコアは 9.8、深刻度は最上位。攻撃の複雑さ(Attack Complexity)は「Low」と評価されています。単純さと危険度は必ずしも比例しない、という良い例だと思います。

## Task 1: 導入 — CVE-2024-21413 とは

CVE(Common Vulnerabilities and Exposures、公開された脆弱性に振られる通し番号)としての基本情報を確認する Task です。

- 公表: 2024年2月13日、Microsoft の定例更新(いわゆる Patch Tuesday)で修正
- 影響: リモートコード実行(Remote Code Execution, RCE)と認証情報の漏えい(credential leak)
- 深刻度: Critical / CVSS 9.8 / Attack Complexity: Low
- 影響範囲: Microsoft 365 Apps、Office 2016 / 2019 / LTSC 2021 など、Office スイートの広い範囲
- 発見者: Check Point Research の Haifei Li

このルームで実際に扱うのは、RCE ではなく「認証情報の漏えい」のほうです。被害者がメール内のリンクをクリックすると、被害者の Windows が攻撃者のマシンへ NTLM の認証情報(パスワードそのものではなく、そこから計算されるハッシュ)を送ってしまう、という流れを体験します。

**学んだこと**

CVSS スコアの数値と、それに対応する深刻度ラベル(Low / Medium / High / Critical)の関係を、脆弱性対応の優先度を決める共通のものさしとして押さえました。「9.0 以上はおおむね最上位ラベル」という感覚が持てると、CVE の一覧を眺めたときに当たりをつけやすくなります。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| CVE (Common Vulnerabilities and Exposures) | 公開された脆弱性ごとの通し番号。「CVE-西暦-連番」の形式 |
| CVSS (Common Vulnerability Scoring System) | 脆弱性の深刻さを 0.0〜10.0 で表す共通スコア |
| Patch Tuesday | Microsoft が毎月第2火曜にまとめて出す定例セキュリティ更新 |
| RCE (Remote Code Execution) | 攻撃者が遠隔から任意のコードを実行できること |

## Task 2: Moniker Link と Protected View

脆弱性の中身を説明する Task です。

Outlook はメールを HTML として表示でき、HTTP / HTTPS だけでなく「アプリケーションを指定する URL」も解釈します。この後者が **Moniker Link(モニカーリンク)** です。モニカーは、名前を渡すと対応するオブジェクトやアプリを呼び出す Windows の仕組み(COM、Component Object Model の一部)で、`file://` で始まるリンクを渡すと「ファイルを扱う担当」が呼ばれます。

そのリンク先が `\\ホスト\共有名` のようなネットワーク上のパスだと、Windows は **SMB**(Server Message Block、Windows のファイル共有プロトコル、445番ポート)でそのホストに接続しようとします。このとき、Windows は「いまログインしているユーザーの資格情報」で自動的に認証を試みます。この認証(NTLM 認証)のやり取りの中で **netNTLMv2 ハッシュ**(チャレンジ&レスポンス方式の応答値)が相手側に渡ります。攻撃者が用意した偽のサーバーがそれを受け取れば、被害者のハッシュが手に入る、という理屈です。共有フォルダが実在しなくても、接続を試みた時点で認証情報は送られてしまう、という点がポイントでした。

通常はここで Outlook の **Protected View(保護されたビュー)** が働きます。Protected View は、組織外から来た添付ファイルやリンクを読み取り専用・機能制限つきで開く保護機能で、外部アプリを起動するようなリンクにはセキュリティ警告を出して止めます。

CVE-2024-21413 の本体は、この Protected View のチェックが、リンクの中に感嘆符と余分な文字列を含めるとすり抜けてしまう、という点です。つまり入力検証(input validation)の不備が、たった1文字で保護機構を無効化してしまう例です。RCE まで到達しうるのはモニカーが COM を使うためですが、この CVE で RCE を実現する概念実証(PoC)は公開されていません。

**学んだこと**

「ネットワーク共有にアクセスしようとしただけで資格情報が送出される」という挙動は、この CVE に固有のものではなく、Windows の SMB + NTLM 認証がもともと持っている性質です(forced authentication、強制認証と呼ばれる系統の攻撃)。CVE-2024-21413 は、そこへ被害者を誘導する新しい経路(Protected View のバイパス)を1つ足したもの、という整理ができました。攻撃の全体像を「入口(バイパス)」と「本体(強制認証によるハッシュ漏えい)」に分けて考えられるようになったのが収穫です。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| Moniker Link | 名前からオブジェクト/アプリを解決する Windows の COM モニカーを指す URL。`file://` などのスキームを取る |
| Protected View | Office / Outlook が信頼できないコンテンツを制限モードで開く保護機能 |
| SMB (Server Message Block) | Windows のファイル共有プロトコル。共有アクセス時に NTLM 認証が走る |
| netNTLMv2 | SMB のチャレンジ&レスポンス認証で得られる応答値。オフライン解析や NTLM リレーに悪用される |
| forced authentication | 被害者に意図せず認証させて資格情報を回収する攻撃手法の総称 |

## Task 3: 攻撃を実際にやってみる

ルームでは、攻撃者側で「偽の SMB サーバー」を立てて待機し、細工したリンク入りのメールを被害者へ送り、被害者がそのリンクをクリックすると、被害者の Windows から攻撃者のマシンへ SMB 接続が飛んでハッシュが記録される、という流れを実際に動かします。

偽サーバーには **Responder** というツールを使いました。Responder は SMB や HTTP の偽サーバーを立て、LLMNR / NBT-NS といった Windows の名前解決を悪用しながら、飛んできた認証情報を記録してくれるツールです。起動時に待ち受けるネットワークインターフェイスを指定します。

メールの送信には、ルームで用意されている Python スクリプト(SMTP でHTMLメールを1通送るだけのもの)を使います。私はこのルームを TryHackMe の AttackBox ではなく自分の Kali から VPN 経由でやったので、ルーム本文が前提にしているインターフェイス名(AttackBox の `ens5`)を、自分の環境の VPN インターフェイス(`tun0`)に読み替える必要がありました。`ip a` で名前を確認する、という基本動作をここで思い出しました。

リンクをクリックすると、Outlook にセキュリティ警告が**出ずに**、いきなり「共有が見つかりません」というダイアログが出ます。これは失敗ではなく、Protected View のバイパスが成功して Windows が共有アクセスに進んだ証拠です(共有名は実在しないので、認証のあとに「見つからない」で終わる)。

**学んだこと**

「攻撃が成立したか」を被害者側の画面の見た目で判断してはいけない、と痛感しました。今回は被害者側に「見つかりません」のエラーが出ましたが、その裏では認証情報がすでに送られています。逆に、この後で書くように、被害者側は同じエラーを出しているのに攻撃者側には何も届いていない、ということも起こります。判断の基準は常に「攻撃者側に想定したデータが届いたか」に置くべきでした。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| Responder | SMB / HTTP の偽サーバーを立て、LLMNR / NBT-NS 応答を偽装して netNTLM ハッシュを収集するツール |
| LLMNR / NBT-NS | Windows の名前解決のフォールバック。Responder が悪用して被害者を偽サーバーへ誘導する |
| SMTP (smtplib) | メール送信プロトコル。ルームの PoC は Python 標準の smtplib で1通送るだけ |
| tun0 | OpenVPN が作る仮想ネットワークインターフェイス。VPN 接続時はここが通信経路になる |

## ラボで詰まった話 — Responder にハッシュが届かない

ここが今回いちばん時間を使った部分です。

リンクはクリックできて、被害者の Outlook には「共有が見つかりません」のダイアログも出る。なのに、待機させている Responder は無反応。ログにも何も出ません。

まず切り分けのために、攻撃者側(Kali)でパケットキャプチャを回した状態で、もう一度リンクをクリックしました。

```
sudo tcpdump -i tun0 -n host <被害者のIP>
```

すると、被害者から Kali の 445番ポートへ SYN パケット(TCP 接続要求)が届いているのは見えました。ところが、その返事である **SYN-ACK が1つも返っていない**。被害者は同じ SYN を何度も再送していました。TCP の 3-way handshake(SYN → SYN-ACK → ACK)の最初の一歩で止まっている、ということです。

Responder 側は 445番で正しく待ち受けていました(`ss -tlnp` で確認)。アプリが待っているのに、SYN に対してカーネルが SYN-ACK を返していない。ということは、パケットがカーネルの TCP スタックに渡る前に捨てられている、と考えられます。

`ping` や `nc` の外向きは通っていました。「外向きは通るのに、外から来る新規接続だけ無音」というのは、ローカルのファイアウォールが着信を弾いているときの典型的な症状です。外向きが通るのは、自分から始めた通信の返り(接続追跡上の ESTABLISHED / RELATED)は別枠で許可されるからで、そこに惑わされていました。

確認すると、Kali で **ufw が有効**になっていて、`Default: deny (incoming)`。iptables の INPUT チェーンも `policy DROP` でした。ufw のルール一覧には「tun0 からの着信を許可」という行が入っていたのですが、実際の iptables ルールとしては効いておらず(リロード漏れが疑わしい)、被害者から 445番への新規 SYN が DROP されていました。

対処として、INPUT チェーンの先頭に明示的な許可を1本挿入しました。

```
sudo iptables -I INPUT -i tun0 -p tcp -m multiport --dports 139,445 -j ACCEPT
```

`-I INPUT` で先頭に挿入するので、後ろにある DROP より先に評価されます。対象は tun0(VPN 経由)から来た 139 / 445番だけに絞っています。ラボが終わったら `-D` で同じルールを削除して元に戻せます(iptables のルールは保存しなければ再起動でも消えます)。

これでもう一度メールを送り直し(Windows は失敗した共有パスを数分キャッシュするので、共有名を変えると確実です)、リンクをクリックすると、今度は Responder に `[SMB] NTLMv2-SSP Hash : ...` が記録されました。

**学んだこと**

- 「相手の画面のエラー」ではなく「自分側にパケット/データが届いたか」で判断する。tcpdump は、その1点を確認するのにいちばん素直な道具でした。
- TCP の不通は、3-way handshake のどこで止まっているかを見ると原因の範囲が一気に狭まります。SYN は届くが SYN-ACK が返らない = 経路は生きているが、着信側のどこか(ファイアウォール、reverse path filter など)で落ちている。
- `ping` が通ることは「着信の新規接続が通ること」を意味しません。接続追跡のおかげで返りだけ通っている場合があります。
- ファイアウォールは中身を見て「怪しい」と判断しているわけではなく、許可リストにない着信を機械的に落としているだけ。default deny の環境では、必要なポートを自分で開ける必要があります。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| tcpdump | コマンドラインのパケットキャプチャツール。`-i` でインターフェイス、`host` で対象を絞る |
| 3-way handshake | TCP 接続確立の手順。SYN → SYN-ACK → ACK |
| ufw (Uncomplicated Firewall) | iptables/nftables のフロントエンド。`default deny incoming` だと着信は原則遮断 |
| conntrack (ESTABLISHED / RELATED) | 接続追跡。自分から始めた通信の返りを識別して許可する仕組み |
| iptables `-I` / `-D` | ルールの挿入 / 削除。`-I chain` は先頭に挿入し、既存ルールより先に評価される |

## Task 4: 検知(Detection)

攻撃だけでなく「どう気づくか」も扱うのがこのルームの良いところでした。

- **YARA ルール** — メール本文をパターンマッチングして攻撃の痕跡を見つけます。ルームでは、`file://` 形式のリンクが既知の拡張子 + 感嘆符で終わるパターンを正規表現で表し、それにメールヘッダらしい文字列(`Subject:` `Received:`)とファイルサイズの上限を組み合わせた複合ルール(Florian Roth 氏作)が紹介されていました。YARA ルールは `meta:`(メモ)、`strings:`(探すパターン)、`condition:`(マッチ条件)の3ブロックでできています。
- **Wireshark / パケットキャプチャ** — 被害者から攻撃者への SMB 通信(445番)と、その認証パケットに乗る netNTLMv2 ハッシュの断片が観測できます。ホスト側のログが取れなくても、ネットワーク側で「内部端末が見慣れない宛先へ SMB でつなぎに行った」ことを異常として捉えられます。

**学んだこと**

1つの攻撃を、メール内容(YARA)と通信(パケット)という別のレイヤーで捕まえる、という多層検知の考え方を具体例で見られました。エクスプロイト固有の文字列(`file://...!`)を正規表現に落として検知ルールにする、という作業の感触もつかめました。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| YARA | ファイル / メモリ / メールをルールベースでパターンマッチする、マルウェアハンティング定番のツール |
| meta / strings / condition | YARA ルールの3ブロック構造 |
| Wireshark | パケット解析ツール。SMB / NTLM のやり取りを追える |
| IDS / IPS | 侵入検知 / 防止システム。SMB の外向き通信などをシグネチャやふるまいで検知する |

## Task 5・6: 対策(Remediation)とまとめ

対策は優先度をつけて整理できました。

1. **パッチ適用が第一** — 2024年2月の Patch Tuesday で修正済み。Windows Update または Microsoft Update Catalog から Office を更新すれば塞がります。
2. **回避策には限界がある** — Protected View そのものをすり抜けるバグなので、Outlook の設定変更でこの攻撃を防ぐことはできません。パッチ以外の完全な緩和策がない、という点がこの CVE の厄介なところです。
3. **ネットワーク側の緩和** — 外向きの SMB(445番)をファイアウォールで制限すると(egress filtering)、被害者の Windows が攻撃者サーバーへハッシュを送る経路を断てます。ただし SMB は社内のファイル共有に必須なので、全面遮断ではなく、インターネット向けだけを止めるといった慎重な設計が必要です。
4. **人的対策** — 心当たりのないメールのリンクを踏まない、クリック前にリンク先をプレビューする、不審メールはセキュリティ担当へ転送する。技術対策が間に合わないときの最後の砦です。

**学んだこと**

「パッチ最優先 → 無理ならネットワーク / 運用でリスク低減 → 並行してユーザー教育」という多層の順序は、この CVE に限らず脆弱性対応全般でそのまま使える型でした。特に「設定変更では防げない脆弱性がある」というのは、対策を考えるときに最初に確認すべき点だと分かりました。

**関連キーワード**

| キーワード(英語) | 説明 |
| --- | --- |
| egress filtering | 内部から外部への通信をファイアウォールで制限すること。外向き SMB 遮断が代表例 |
| Microsoft Update Catalog | 個別の KB パッチを手動ダウンロードできる Microsoft の配布サイト |
| defense in depth | 単一の対策に頼らず複数の防御層を重ねる設計思想 |
| security awareness training | 不審リンク / 不審メールへの対応をユーザーに教育する取り組み |

## 全体を通して学んだこと

このルームで扱った攻撃自体は、「Protected View をバイパス → 強制認証で netNTLMv2 ハッシュが漏れる → そのハッシュはオフライン解析や NTLM リレーの起点になる」という一本の流れでした。ハッシュを取ること自体はゴールではなく入口である、という感覚が持てたのが大きいです。

もう一つの収穫は、脆弱性の知識とは別のところにありました。攻撃側に何も返ってこないとき、tcpdump で「パケットは届いているのか」「TCP のどの段階で止まっているのか」を確認し、そこからローカルファイアウォールの default deny にたどり着く、という切り分けの手順です。これはセキュリティの演習に限らず、自宅サーバーやコンテナのネットワークが不通になったときにもそのまま使えます。ツールの使い方を1つ覚えるより、こういう「詰まったときにどこから見るか」の型が少しずつ増えていくほうが、後々効いてくる気がしています。
