## 作りたかったもの

個人開発しているPWA(Progressive Web App)アプリに、2048や反応速度ゲームなどの
ミニゲームを入れました。せっかくなので、友人と点数を比べ合えるようにしたいと
思いました。ただし普通に遊べるだけだと、盤面も出現順も毎回バラバラなので、
「今日、俺は何点だった」と言い合っても、そもそも同じ問題を解いていないので
あまり比較になりません。

そこで思いついたのが、**その日にプレイした人は全員、まったく同じ問題(同じ盤面・
同じ出現順)に挑戦する**というデイリーチャレンジの仕組みでした。日替わりで
みんなが同じお題に挑む形にすれば、素直に「今日は誰が一番強かったか」を競えます。

## 気づいた制約

ここで問題になったのが、このアプリはサーバーを持たない、完全にブラウザだけで
完結する設計にしていたことです。普通にサーバーがあれば、「今日のお題」を
どこかで1回計算してみんなに配ればいいだけなのですが、それができません。
配る側が存在しないのに、全員に同じ答えを持たせないといけない。書き始める前から、
これは少し厄介だぞ、と思っていました。

とはいえ、コンピュータの乱数生成には**同じ「種(シード)」から始めれば、常に
同じ数列が出てくる**という性質があります(疑似乱数生成器、PRNG: Pseudo-Random
Number Generatorと呼ばれるものです)。「今日の日付」をそのままシードにすれば、
サーバーを介さなくても全員が同じ盤面にたどり着けるはずだ、というのが最初の
発想でした。

## とりあえず書いてみた

日付からシードを作る部分は、素直に書けばこうなります。

```typescript
// 端末のローカル時刻から YYYY-MM-DD 相当の整数を作る
function dailySeed(date: Date = new Date()): number {
  const year = date.getFullYear();
  const month = date.getMonth() + 1;
  const day = date.getDate();
  return year * 10000 + month * 100 + day;
}
```

1つだけ、書いている途中で「あ、これは危ない」と気づいて直した点があります。
最初は`date.toISOString()`(UTC基準)で日付を取ろうとしていたのですが、日本時間は
UTC+9なので、日本時間の夜21時〜深夜の間はUTC上ではまだ前日という扱いになります。
つまりデイリーチャレンジの切り替わりが、体感時刻より2〜3時間ズレてしまう。
これに気づかず実装していたら、夜更かしして遊んでいる人だけ「なぜか日付が
合わない」という不可解な不具合に出くわしていたはずです。`getFullYear()` /
`getMonth()` / `getDate()` という、端末のローカル時刻をそのまま使うメソッドに
書き換えて、この件は解決しました。

このシード(たとえば2026年8月15日なら`20260815`)を、シード付き乱数生成器に
そのまま渡せば完成のはずでした。動かしてみて、実際に同じ日なら同じ盤面が
出ることも確認できて、「よし、できた」と一度は満足していました。

## あれ、なんか変だぞ

念のため、日付を1日ずつずらしながら何日か分の盤面を見比べてみたのですが、
そこで違和感に気づきました。8月15日の盤面と8月16日の盤面、**最初の数手が
やけに似ている**のです。1日や2日ならたまたまかもしれませんが、試した範囲で
何度も同じ傾向が出ました。これはさすがに偶然ではないな、と思いました。

使っていたシード付き乱数生成器は`mulberry32`という軽量なアルゴリズムです。

```typescript
export function createRng(seed: number): () => number {
  let a = seed;
  return function rng(): number {
    a |= 0;
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
```

このコード自体を疑ったわけではありません。`mulberry32`は広く使われていて、
統計的な質にも定評があるアルゴリズムです。ただ調べていくうちに、この手の
軽量PRNGには共通して「**内部状態が近いシードを渡すと、最初の数回の出力も
近くなりやすい**」という性質があることを知りました。恥ずかしながら、シード
付き乱数を実装するまで、こういう特性があること自体を知りませんでした。

今回のシードは`20260815`と`20260816`のように、日付が変わっても数値としては
ごく僅かしか変わりません。これをそのままPRNGの初期状態として渡していたので、
まさにこの「近いシード問題」を踏み抜いていたわけです。デイリーチャレンジは
「今日だけの特別なお題」であってほしいので、これは見過ごせない挙動でした。

## 調べてみてわかったこと

対策として、シードをPRNGに渡す前に、ハッシュ関数で一度撹拌(かくはん)する
ことにしました。

```typescript
function hashSeed(seed: number): number {
  let h = seed >>> 0;
  h = Math.imul(h ^ (h >>> 16), 2654435761);
  h = Math.imul(h ^ (h >>> 13), 2246822519);
  h ^= h >>> 16;
  return h >>> 0;
}
```

これは`murmur3`というハッシュアルゴリズムの終盤で使われている「アバランチ
(avalanche)」という処理を単体で取り出したものです。名前の通り、**入力を1ビット
でも変えると、出力のビットが雪崩のように大きく変わる**という性質を持っています。
`20260815`と`20260816`のように入力がほぼ同じでも、このハッシュを通した後の値は
まったくの別物になり、PRNGの初期状態が十分にばらけるようになりました。

実際に何日か分の盤面を見比べ直してみると、今度こそ隣り合う日でもきちんと
違う展開になっていて、ようやく安心できました。最終的な流れは「日付 → 整数
シード → ハッシュで撹拌 → mulberry32で乱数列を生成」という3段構成に落ち着いた
ことになります。

## 今のかたち

このアプリには他にも、サイコロを振るミニゲームがあります。ただしこちらは
「その場に集まった友人同士で対面プレイする」用途なので、**再現性がある方が
むしろ困ります**。なので意図的に`Math.random()`をそのまま使い、シードは
使っていません。全部を同じ仕組みで統一したい誘惑もあったのですが、
「揃えるべきもの」と「毎回本当にランダムであるべきもの」は性質が違うと
割り切って、機能ごとに使い分けています。

このバグは、コードを一度書いて動作確認しただけでは気づけませんでした。
たまたま複数日の盤面を並べて見る、という一手間をかけたから見つかったもの
です。「動いたから完成」で済ませていたら、今もどこかで気づかれずに残って
いたかもしれません。
