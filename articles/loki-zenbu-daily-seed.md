## この記事について

神社のおみくじは、同じ日に同じ箱を引いても、人によって出る結果が違います。それは
それで面白いのですが、もし「今日は全員が同じ運勢を引く日」という縛りのおみくじが
あったら、箱の中身をどう管理すればいいでしょうか。今回はこれとよく似た問題を、
個人開発しているアプリのミニゲームで実際に解くことになった話です。

個人開発しているPWA(Progressive Web App)アプリの中に、2048・反応速度ゲームなどのミニ
ゲームを「デイリーチャレンジ」として遊べる機能があります。友人と点数を比べて遊べるように、
**その日にプレイした人は全員、まったく同じ問題(同じ盤面・同じ出現順)に挑戦する**という
仕組みにしています。

このアプリはサーバーを持たない、完全にブラウザだけで完結する設計です。つまり「今日のお題」
を誰かが計算してみんなに配る、ということができません。おみくじの箱を管理する神社の人が
どこにもいない状態で、全員に同じ結果を引かせる必要があったわけです。そんな無茶な話を
どう解決したか、そして実装の途中で気づいた落とし穴について書きます。

## 解きたかった問題

「サーバーなしで、全員に同じ乱数列を配る」というのは、一見矛盾した要求に思えます。ですが
コンピュータの乱数生成には、**同じ「種(シード)」から始めれば、常に同じ数列が出てくる**
という性質があります。これを「疑似乱数生成器(PRNG: Pseudo-Random Number Generator)」
と呼びます。通常の`Math.random()`は毎回違う結果を返しますが、シードを指定できる実装に
差し替えれば、シードさえ揃えば結果も揃います。

つまり、「今日の日付」をシードにすれば、サーバーを介さなくても全員が同じ盤面に到達できる
はずです。

## 最初に考えた実装

日付からシードを作る部分は、素直に書けば以下のようになります。

```typescript
// 端末のローカル時刻から YYYY-MM-DD 相当の整数を作る
function dailySeed(date: Date = new Date()): number {
  const year = date.getFullYear();
  const month = date.getMonth() + 1;
  const day = date.getDate();
  return year * 10000 + month * 100 + day;
}
```

ここで1つ注意した点があります。日付の取得に`date.toISOString()`(UTC基準)を使わなかった
ことです。日本時間は UTC+9 のため、UTC基準で日付を取ると、日本時間の夜21時〜深夜の間は
「UTC上ではまだ前日」というズレが起きます。デイリーチャレンジが日をまたぐタイミングが
ユーザーの体感時刻とズレてしまうため、`getFullYear()` / `getMonth()` / `getDate()` という
端末のローカル時刻を使うメソッドで統一しています。

このシード(例: 2026年8月15日なら`20260815`)を、シード付き乱数生成器にそのまま渡せば
完成——のはずでした。

## ハマりかけた点: 隣り合う日付の「初期の出目」が似てしまう

シード付き乱数生成器には`mulberry32`という軽量なアルゴリズムを使っています。実装は
数十行程度のシンプルなものです。

```typescript
export function createRng(seed: number): () => number {
  let a = seed;
  return function rng(): number {
    a |= 0;
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
```

このアルゴリズム自体は広く使われている実装で、統計的な質にも問題はありません。ただし、
`mulberry32`に限らずこの手の軽量PRNGには「**内部状態が近いシードを渡すと、最初の数回の
出力も近くなりやすい**」という性質があります。

今回のシードは`20260815`(8月15日)や`20260816`(8月16日)のように、日付が変わっても
数値としてはごく僅かしか変わりません。これをそのままPRNGに渡すと、隣り合う日のお題が
「似たり寄ったりの展開になる」現象が起きる可能性がありました。おみくじで例えるなら、
毎日律儀に大吉を引き続けるようなもので、それはそれでめでたいのですが、デイリー
チャレンジとしては「今日だけの特別なお題」であってほしいので、これは避けたい挙動です。

## 実際の解決策: シードを一度ハッシュ関数にくぐらせる

対策として、シードをPRNGに渡す前に、ハッシュ関数で撹拌(かくはん)することにしました。

```typescript
function hashSeed(seed: number): number {
  let h = seed >>> 0;
  h = Math.imul(h ^ (h >>> 16), 2654435761);
  h = Math.imul(h ^ (h >>> 13), 2246822519);
  h ^= h >>> 16;
  return h >>> 0;
}
```

これは`murmur3`というハッシュアルゴリズムの終盤で使われている「アバランチ(avalanche)」
という処理を単体で使ったものです。アバランチという名前の通り、**入力を1ビットでも変える
と、出力のビットが雪崩のように大きく変わる**という性質を持っています。`20260815`と
`20260816`のように入力がほぼ同じでも、このハッシュを通した後の値はまったく違う値になり、
結果としてPRNGの初期状態が十分にばらけます。

最終的な流れは「日付 → 整数シード → ハッシュで撹拌 → mulberry32で乱数列を生成」という
3段構成になりました。

## 補足: あえてシードを使わない箇所

このアプリには他にも、サイコロを振るミニゲームがあります。ただしこちらは「その場に
集まった友人同士で対面プレイする」用途のため、**再現性がある方がむしろ都合が悪い**と
判断し、意図的に`Math.random()`をそのまま使っています。「シードで揃えるべきもの」と
「毎回本当にランダムであるべきもの」を機能ごとに切り分けたのも、実装していて意識した
点でした。

## 学んだこと

- シード付き乱数は「同じシードなら同じ結果」という性質だけでなく、**似たシードが似た初期
  結果を生みやすい**という軽量PRNG特有のクセにも注意が必要だということ。
- この手のクセは、コードを一度書いただけでは気づきにくく、複数の日付で実際に出力を
  比較してみて初めて見えてきました。「動くから完成」ではなく、意図した性質(この場合は
  「日ごとに十分ばらけているか」)を明示的に検証する視点の大切さを感じました。
