## この記事について

TryHackMe の「Public Key Cryptography Basics」というルームで学んだ内容を、Task 単位でまとめたノートです。Cyber Security 101 の「Cryptography」モジュールにあるルームで、公開鍵暗号（public key cryptography、非対称暗号とも呼ばれます）の基本を、RSA・Diffie-Hellman 鍵交換・SSH・デジタル署名と証明書・PGP/GPG という応用例に沿って扱います。暗号入門の3部作（Cryptography Basics / Public Key Cryptography Basics / Hashing Basics）の2本目にあたります。

課題の設問や答え、フラグはここには含めていません。各 Task で出てきた用語や考え方を、自分の理解として整理したものです。

このルームを進めていたころ、耐量子計算機暗号（post-quantum cryptography、PQC）への移行が実務の作業として動き出しているのを知りました。NIST は 2024 年 8 月に PQC の標準 FIPS 203・204・205 を正式公開し、主要なブラウザやサービスは通信の鍵交換を新方式へ切り替え始めています。その置き換え対象が、まさにこのルームで扱う RSA・Diffie-Hellman・楕円曲線暗号です。いま安全とされるのは、これらが素因数分解や離散対数の難しさに支えられているからで、その前提が将来まで保証されているわけではありません。「どの暗号が何の難しさを根拠にしているか」をこのルームで一つずつ確認しておくと、こうした移行のニュースを自分の言葉で読めるようになります。そういえば、SSH で新しいサーバーにつなぐと出る確認プロンプトやブラウザの鍵マークも、これまで素通りしていましたが、あれが公開鍵で相手の正体を確かめている場面なのだと分かるようになりました。

## Task 1: 導入

このルームで学ぶ範囲の紹介です。対面での打ち合わせをたとえに、セキュリティで守りたい4つの目標が整理されます。

- 認証（authentication）: 話している相手が誰なのかを確認できる
- 真正性（authenticity）: メッセージが名乗られたとおりの送信者から来ていると検証できる
- 完全性（integrity）: 中身が途中で書き換えられていないと保証できる
- 機密性（confidentiality）: 関係者以外に中身を読まれない

前のルームで学んだ共通鍵暗号（symmetric encryption）は、主に機密性を守る技術でした。このルームの主役である公開鍵暗号は、残りの認証・真正性・完全性で大きな役割を果たします。RSA、Diffie-Hellman、SSH、SSL/TLS 証明書、PGP/GPG が、その具体例として順に登場します。

**学んだこと**

仕組みを追う前に「この Task はどの目標を守る話か」を毎回確認すると、内容がぶれずに読めました。特にこのルームは「機密性は共通鍵の担当、それ以外は公開鍵の担当」という役割分担を意識しておくと、後半の署名や証明書の話が一本の筋でつながります。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| public key cryptography / asymmetric cryptography | 公開鍵と秘密鍵のペアを使う暗号方式の総称 |
| authentication / authenticity / integrity / confidentiality | 認証・真正性・完全性・機密性。暗号が守る代表的な性質 |
| symmetric encryption | 暗号化と復号に同じ鍵を使う方式。高速だが鍵の共有が課題 |

## Task 2: 非対称暗号のよくある使い方

公開鍵暗号が実際に何に使われているか、という Task です。結論から言うと、いちばん多い用途は「共通鍵暗号の鍵を安全に受け渡すこと」です。

公開鍵暗号は共通鍵暗号に比べて計算が重く、通信のすべてをこれで処理すると遅くなります。そこで実際のプロトコル（HTTPS や SSH など）は、次のように動きます。

1. 公開鍵暗号を最初に一度だけ使い、共通鍵暗号の鍵を安全に共有する
2. 以降は軽くて速い共通鍵暗号で本文をやり取りする

この「重い方式で鍵だけ渡し、軽い方式で本文を運ぶ」組み合わせをハイブリッド暗号（hybrid encryption）と呼びます。ルームでは、鍵の持ち主だけが開けられる南京錠と壊せない箱のたとえで説明されていました。南京錠が公開鍵（誰に配ってもよい）、その鍵が秘密鍵（本人だけが持つ）に対応します。

**学んだこと**

「なぜ公開鍵暗号を毎回使わないのか」という素朴な疑問に、速度という明確な理由があると分かりました。あわせて、この方式だけでは「その公開鍵が本当に相手のものか」は保証されない、という限界も示されます。そこは Task 6 の署名と証明書で回収されます。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| key exchange | 盗聴されうる経路で、共通鍵暗号の鍵を安全に共有・合意する手続き |
| hybrid encryption | 非対称暗号で鍵を渡し、共通鍵暗号で本文を暗号化する組み合わせ |
| public key / private key | 公開鍵（配ってよい） / 秘密鍵（本人だけが守る） |

## Task 3: RSA

公開鍵暗号の代表格、RSA の仕組みを数値例で追う Task です。

RSA の安全性は「大きな数の素因数分解（integer factorization）が難しい」という事実に寄りかかっています。2つの大きな素数を掛けるのは簡単ですが、その積から元の2つの素数を復元するのは、数が大きくなると現実的な時間では終わりません。ルームでは、実運用では p と q がそれぞれ 300 桁程度の素数になる、と説明されていました。

鍵生成の流れは次のようになります。

1. 2つの素数 p、q を選ぶ
2. n = p × q を計算する（この n が公開鍵にも秘密鍵にも入る「法」）
3. ϕ(n) = (p − 1)(q − 1) を計算する（オイラーのトーシェント関数）
4. ϕ(n) と互いに素な e を選ぶ（公開指数）
5. e × d ≡ 1 (mod ϕ(n)) を満たす d を求める（秘密指数）

暗号化は `c = m^e mod n`（公開鍵を使う）、復号は `m = c^d mod n`（秘密鍵を使う）です。この「べき乗して法で割った余りを取る」計算を剰余べき乗（modular exponentiation）と呼び、RSA と Diffie-Hellman の中核になります。

**学んだこと**

Python では `pow(a, b, m)` の第3引数に法を渡すと、剰余べき乗を一度に計算してくれます。`(a ** b) % m` と数学的な結果は同じですが、途中の巨大な数を作らずに済むので、桁の大きい暗号計算でも一瞬で終わります。Python 3.8 以降なら `pow(e, -1, phi)` でモジュラ逆数（modular inverse）も求められ、これが秘密指数 d の計算に使えます。CTF で RSA を手で解くときの実務的な道具として覚えておこうと思いました。ただし、入力によって計算時間が変わるため、タイミング攻撃（timing attack）を気にする本番の暗号ライブラリは、素の `pow` ではなく定数時間の実装を使う、という但し書きも押さえておきます。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| integer factorization | 合成数を素因数に分解する問題。大きな数では計算量的に困難で、RSA の安全性の根拠 |
| Euler's totient ϕ(n) | RSA では ϕ(n) = (p − 1)(q − 1)。鍵生成に使う |
| public / private exponent (e, d) | e は公開、d は秘密。e·d ≡ 1 (mod ϕ(n)) の関係 |
| modular exponentiation | 剰余べき乗。Python の `pow(a, b, m)` |
| RsaCtfTool / rsatool | 弱いパラメータの RSA を攻略・計算する CTF 向けツール |

## Task 4: Diffie-Hellman 鍵交換

鍵そのものを一度も送らずに、2者が同じ共有鍵にたどり着く方法を学ぶ Task です。

手順を記号で書くと次のようになります。

- 公開する値: 大きな素数 p と生成元（generator）g
- 各自の秘密: Alice は a、Bob は b（外に出さない）
- 公開鍵の計算と交換: `A = g^a mod p`、`B = g^b mod p` を計算して送り合う
- 共有鍵の計算: Alice は `B^a mod p`、Bob は `A^b mod p` を計算する。どちらも `g^(ab) mod p` になって一致する

`(g^a)^b` と `(g^b)^a` がどちらも `g^(ab)` になる、という指数法則が一致の理由です。盗聴者は p、g、A、B をすべて見られますが、そこから a や b を復元することはできません。これは「`g^x mod p = A` から x を求める」離散対数問題（discrete logarithm problem）が難しいからで、RSA の素因数分解と並ぶ、公開鍵暗号のもう一つの難問です。

ルームでは、素の Diffie-Hellman は中間者攻撃（man-in-the-middle attack）に弱く、RSA による署名などの認証と組み合わせて使う、と説明されていました。

**学んだこと**

Diffie-Hellman は「暗号化アルゴリズム」ではなく「共有秘密を作る手続き（key agreement）」だ、という区別が大事でした。RSA が署名・鍵転送・認証を担当し、Diffie-Hellman が鍵合意を担当する、という分担で多くのプロトコルに同居しています。使い捨ての鍵で毎回鍵交換する方式（ephemeral Diffie-Hellman）にすると、長期鍵が将来漏れても過去の通信は復号されない、という前方秘匿性（forward secrecy）につながる点も、名前だけ覚えておきます。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| key agreement / key exchange | 双方が寄与して共有鍵を作る手続き |
| discrete logarithm problem | `g^x mod p = A` から x を求める問題。Diffie-Hellman の安全性の根拠 |
| man-in-the-middle attack | 通信の間に割り込み、双方になりすます攻撃。素の Diffie-Hellman の弱点 |
| ephemeral Diffie-Hellman (DHE / ECDHE) | 毎回使い捨ての鍵を使う方式。前方秘匿性をもたらす |
| forward secrecy | 長期鍵が漏れても、過去のセッションの暗号文は守られる性質 |

## Task 5: SSH

公開鍵暗号が実務でどう使われているかを、SSH を題材に見る Task です。SSH の認証には方向が2つあります。

- サーバー認証: クライアントがサーバーの公開鍵を確認する。初回接続で出る「本当に接続を続けますか？」の確認がこれで、答えた公開鍵は `~/.ssh/known_hosts` に記録される。次回以降、別の公開鍵が返ってきたら警告が出る（サーバーの入れ替えや中間者攻撃のサイン）
- クライアント認証: サーバーが利用者を確認する。パスワードの代わりに鍵ペアを使う場合、利用者の公開鍵をサーバーの `~/.ssh/authorized_keys` に置いておき、接続時に対応する秘密鍵で「この公開鍵の持ち主だ」と証明する

鍵の種類は `ssh-keygen` の `-t` オプションで選べます（rsa、ecdsa、ed25519 など）。秘密鍵ファイルは形式によって1行目のヘッダーが変わり、古い形式なら `-----BEGIN RSA PRIVATE KEY-----` のように型名がそのまま入っています。`Proc-Type: 4,ENCRYPTED` と `DEK-Info:` の行があれば、その秘密鍵はパスフレーズで暗号化されている、という意味です。`ssh-keygen -l -f <ファイル>` を使うと、鍵のフィンガープリントと種類・ビット数を表示できます。

**学んだこと**

秘密鍵は「パスワードと同じ扱い」で、パーミッションは所有者だけ読み書きできる `600` にしないと SSH クライアントが鍵を無視します。パスフレーズはサーバーには送られず、ローカルで秘密鍵を復号するためだけに使われる、という点は誤解しやすいので整理できてよかったです。暗号化された秘密鍵は `ssh2john`（John the Ripper 付属の変換ツール）でハッシュにしてからクラックを試せるので、弱いパスフレーズは危険、という攻撃側の視点も学びました。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| ssh-keygen | SSH 鍵ペアを生成するコマンド。`-t` で種類、`-l -f` で情報表示 |
| known_hosts / authorized_keys | 接続先の公開鍵の記録 / ログインを許可する公開鍵の一覧 |
| fingerprint | 公開鍵をハッシュした短い識別子。鍵の同一性確認に使う |
| Ed25519 | Curve25519 上の EdDSA による署名方式。短い鍵で高速。現在の推奨 |
| ssh2john / gpg2john | 鍵ファイルを John the Ripper で扱える形式に変換する補助ツール |

## Task 6: デジタル署名と証明書

真正性と完全性を公開鍵暗号でどう証明するか、という Task です。ここで鍵の使い方が Task 3 と逆になります。

- 暗号化（機密性）: 相手の公開鍵で暗号化し、相手の秘密鍵で復号する
- 署名（真正性・完全性）: 自分の秘密鍵で署名し、誰でも自分の公開鍵で検証する

秘密鍵を持つのは本人だけなので、「その公開鍵で検証できる署名は本人が作った」と言えます。これが真正性です。さらに実際の署名は文書そのものではなく文書のハッシュ（hash）に対して行います。ハッシュは中身が少しでも変わると別の値になるため、署名を検証できたということは改ざんされていない、と言えます。これが完全性です。文書の上に署名画像を貼るだけのやり方（electronic signature と呼ばれることがある）は、画像をコピーできるので完全性を証明しません。

証明書（certificate）は、「その公開鍵は確かにこの相手のものだ」を保証する仕組みです。Web サーバーは「自分は本物の example.com だ」と述べる証明書を持ち、その証明書には認証局（CA、Certificate Authority）の署名が付いています。ブラウザは出荷時からルート CA を信頼していて、`ルート CA → 中間 CA → サーバー証明書` と署名をたどれれば、そのサーバーを信頼します。この構造を信頼の連鎖（chain of trust）と呼びます。TLS 証明書は有料の認証局から買うほか、Let's Encrypt から無料で取得できます。

**学んだこと**

「署名は秘密鍵で作って公開鍵で検証する」という向きが、暗号化とちょうど逆である点をはっきり覚えました。証明書は結局「公開鍵に持ち主の名札を付けて、それを第三者（CA）が保証したもの」だと捉えると、HTTPS の鍵マークが何を確認しているのかが腑に落ちます。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| digital signature | 秘密鍵で生成し公開鍵で検証する、真正性・完全性の証明 |
| hash | データを固定長の値に変換したもの。1ビットの変更でも値が大きく変わる |
| certificate (X.509) | 公開鍵と所有者情報をまとめ、CA が署名した電子文書 |
| Certificate Authority (CA) | 証明書に署名し、その正当性を保証する組織 |
| chain of trust | ルート CA から末端の証明書まで、署名をたどって信頼を伝える構造 |
| Let's Encrypt | 無料で TLS 証明書を発行する認証局 |

## Task 7: PGP と GPG

メールやファイルの暗号化・署名に使う PGP と、その実装である GPG を扱う Task です。

用語の関係を整理すると、PGP（Pretty Good Privacy）が元の製品名、OpenPGP がその仕様を標準化したもの、GPG（GnuPG）が OpenPGP の無料・オープンソース実装で、実際に打つコマンドが `gpg` です。鍵ペアは SSH と同じ考え方で、公開鍵を相手に配り、秘密鍵は本人だけが持ちます。相手は私の公開鍵でメッセージを暗号化し、私は秘密鍵でそれを復号します。

鍵の生成は `gpg --full-gen-key` で対話的に行い、アルゴリズム・楕円曲線・有効期限・利用者情報（名前とメールアドレス）を順に指定します。受け取った鍵を取り込むのが `gpg --import`、暗号化されたファイルを復号するのが `gpg --decrypt` です。GPG の秘密鍵も SSH と同様にパスフレーズで保護でき、保護されている場合は `gpg2john` でハッシュに変換してクラックを試せます。

**学んだこと**

PGP/GPG は、Task 2 から 6 で学んだ部品（公開鍵暗号による鍵の受け渡し、共通鍵暗号による本文、秘密鍵による署名）をひとつのツールにまとめたもの、と捉えると全体像がつかめました。鍵を失うと過去に受け取った暗号文を二度と復号できなくなるので、秘密鍵のバックアップを安全な場所に持っておくことが重要、という運用面の注意も押さえておきます。

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| PGP (Pretty Good Privacy) | ファイル・メールの暗号化と署名を行う暗号ソフトウェア |
| OpenPGP | PGP のフォーマットとプロトコルを定めた公開標準 |
| GnuPG / gpg | OpenPGP のオープンソース実装とそのコマンド |
| `gpg --import` / `gpg --decrypt` | 鍵を取り込む / 暗号化ファイルを復号する |
| keyring | GPG が公開鍵・秘密鍵を保管する鍵束（`~/.gnupg`） |

## Task 8: まとめ

ルーム全体の振り返りと、新しい用語の追加です。暗号（cryptography）が「守る側」の科学であるのに対し、それを破る・迂回する方法を研究するのが暗号解読（cryptanalysis）です。パスワードのあらゆる組み合わせを試すのが総当たり攻撃（brute-force attack）、辞書にありそうな単語に絞って試すのが辞書攻撃（dictionary attack）です。

**学んだこと**

このルームで扱った内容を、次の点を自分の言葉で説明できるかで確認しました。

- 公開鍵暗号は「鍵交換に一度だけ」使い、本文は共通鍵暗号で運ぶ（ハイブリッド暗号）
- RSA は素因数分解の困難性が土台。鍵生成は p, q → n → ϕ(n) → e → d
- Diffie-Hellman は離散対数問題が土台。鍵を送らずに共有秘密を作る。素の方式は中間者攻撃に弱い
- SSH はサーバー認証（known_hosts）とクライアント認証（authorized_keys）の2方向
- 署名は秘密鍵で作り公開鍵で検証する。ハッシュに署名して完全性を担保する
- 証明書は CA の署名による信頼の連鎖で「公開鍵の持ち主」を保証する
- PGP/GPG は上記の部品をまとめた実用ツール

**関連キーワード**

| キーワード（英語） | 説明 |
| --- | --- |
| cryptanalysis | 鍵を知らずに暗号を破る・迂回する方法を研究する分野 |
| brute-force attack | 可能な鍵・パスワードを片端から全部試す攻撃 |
| dictionary attack | 辞書の単語やその組み合わせに絞って試す攻撃 |
| John the Ripper | パスワード・鍵のクラッキングツール。SSH 鍵や GPG 鍵の攻撃にも使う |

## おわりに

「Public Key Cryptography Basics」は、RSA と Diffie-Hellman の数式が出てくるので身構えていましたが、実際には「掛け算は簡単・素因数分解は困難」「べき乗は簡単・離散対数は困難」という一方向性が土台にある、という一点を押さえれば読み進められました。仕組みが分かると、SSH のホスト鍵確認や HTTPS の鍵マークといった、これまで素通りしていた画面の意味が変わります。次は3部作の最後、Hashing Basics で、この Task 6 で出てきた「ハッシュに署名する」という話をもう一段掘り下げていくつもりです。
