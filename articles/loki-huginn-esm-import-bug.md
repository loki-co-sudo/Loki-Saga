## 導入

最近、AIエージェントに何でも任せられるようになった、みたいな景気のいい話をよく
目にします。一方で私が最近つまずいたのは、そういう華やかな話とは真逆の、地味な
import文の書き方でした。世の中どんどん便利になっていくのに、自分は`../shared/types`
の後ろに`.js`をつけるかどうかで丸一日悩んでいたわけです。今回はそんな、
ちょっと格好悪い話です。

## 目的

個人開発しているニュース収集アプリ`Loki-Huginn`では、毎日自動でRSSフィードを
取りに行って、記事を整形・保存する処理が必要でした。これは「ユーザーがアプリを
開いたときに動く」ものではなく、「誰も見ていなくても、毎日決まった時間に
勝手に動いてほしい」処理です。なので、ブラウザ側のコードだけでは完結できません。

そこで、Vercel Functionsという仕組みを使い、Node.jsのサーバーサイドコードとして
RSS収集処理を書き、Vercelの定期実行(Cron)で1日1回自動で叩く、という構成に
しました。集めた記事はVercel Blobというストレージに保存し、フロントエンドは
それを読みに行くだけの薄いつくりにしています。

## 実装

RSS取得・キーワードによるタグ付け・重複除去といったロジックを書き、ローカルの
開発サーバーで何度も動作確認しました。型チェックも通り、ビルドも問題なく成功。
「これでもう一区切りだな」くらいの気持ちで、デプロイボタンを押しました。

ところが、実際にデプロイ後の環境で該当の処理を呼び出してみると、こういうエラーで
落ちていました。

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '.../shared/types' imported from '.../server/collect.js'
```

ローカルでは何度動かしても再現しません。ビルドも型チェックも通っています。それなのに
本番でだけ、しかも毎回確実に落ちる。正直、この時点では何から疑えばいいのか
見当がつきませんでした。

まず疑ったのは環境変数の設定漏れ。次に、依存パッケージのバージョン差。どちらも
違いました。ローカルとVercel上のNode.jsのバージョンを揃えてみても変わりません。
「型もビルドも通っているのに、実行時にだけ失敗する」というのは今まであまり
経験したことのないパターンで、かなり戸惑いました。

手がかりになったのは、Vercelが出しているランタイムログでした。エラーメッセージを
そのままよく読み返すと、`ERR_MODULE_NOT_FOUND`というエラーコードと、モジュールを
見つけられなかったファイルパスが書かれています。ここでようやく「ビルドやテストの
段階では検出できない、実行時特有の何かが起きている」という方向に頭を切り替える
ことができました。

このプロジェクトでは、次のような拡張子なしの相対importを書いていました。

```typescript
// server/collect.ts
import { Article } from '../shared/types';
```

普段このコードは、TypeScriptの型チェックも、Viteの開発サーバーでの実行も、
何の問題もなく通っていました。恥ずかしながら、私はこのとき初めて「型チェックが
通ること」と「実際にそのコードを実行できること」がイコールではない、という
当たり前の事実を、身をもって理解することになりました。

`tsconfig.json`では`moduleResolution: "bundler"`という設定を使っています。この
設定のもとでは、拡張子なしの相対importでも型チェックは通ります。そしてローカルの
開発サーバーはViteが担っていて、Viteは内部でファイルをバンドルする際に、拡張子の
省略をよしなに解決してくれます。つまり「型チェックが通る」も「ローカルのdev
サーバーで動く」も、どちらもVite(とTypeScriptの緩めの設定)がお膳立てしてくれた
上での話であって、実行時のモジュール解決が仕様通りに正しいかどうかとは、実は
何の関係もなかったのです。

一方、Vercel Functionsの実行環境は素のNode.js(ESM)です。Node.jsのESMローダーは、
CommonJSの`require`とは違い、相対importの拡張子省略を許していません。`.js`ファイル
を読み込むつもりなら、たとえソースが`.ts`であっても、最終的にビルドされる`.js`と
いう拡張子を明示する必要があります。

対策として、`api/`・`server/`・`shared/`配下の相対importすべてに、`.js`拡張子を
明記しました。

```typescript
// 修正後
import { Article } from '../shared/types.js';
```

ソースファイルは`.ts`なのに拡張子が`.js`というのは、最初はどうにも据わりが
悪く感じました。ですがこれは「TypeScriptのソースファイル名」ではなく「ビルド後に
実際に存在するファイル名」を指していると考えると、腑に落ちます。なお、フロント
エンド側(`src/`配下)はViteがビルド・バンドルの両方を担うため、この問題の対象外
です。影響が出るのは、Node.jsが素のESMとして直接実行する`api/`・`server/`配下
のみでした。

## 反省・教訓

「ローカルで動く」「型チェックが通る」を、本番環境でもそのまま動く保証だと思い
込んでいたのが、今回の一番の反省点でした。実際にはビルドツールとランタイムで
モジュール解決のルールが違っていた、という地味な話だったわけですが、こういう
「開発環境だけが優しくしてくれている」ケースは、探せばまだあるんだろうなと
思っています。

あと単純に、エラーメッセージはちゃんと最後まで読むものだなと再確認しました。
`ERR_MODULE_NOT_FOUND`という文字列と、見つからなかったファイルパスさえ見えて
いれば、もう少し早く気づけたはずです。焦って原因を推測で決め打ちするより、
まず目の前のログを丁寧に読む方が、結局は近道でした。

再発防止のために、このルールはプロジェクトの開発ガイドラインに明文化しておき
ました。次に同じ構成のコードを書くときの自分に向けたメモのつもりです。
