## この記事について

個人開発しているニュース収集アプリで、ローカル環境では問題なく動いていた機能が、
Vercelへのデプロイ後だけ`500 Internal Server Error`になるという不具合に遭遇しました。
原因はNode.jsのESM(ES Modules)における、相対importの解決ルールでした。同じ問題に
ぶつかった人の助けになればと思い、原因の切り分け方も含めて記録しておきます。

## 起きたこと

このアプリはVercel Functionsという仕組みの上で、Node.js製のサーバーサイド処理(RSS
フィードの取得・整形・保存)を動かしています。ローカルでは`npm run dev`で問題なく
動作を確認し、デプロイもビルドも成功していたのですが、実際にデプロイ後の環境で該当の
処理を呼び出すと、次のようなエラーで落ちていました。

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '.../shared/types' imported from '.../server/collect.js'
```

ローカルでは再現しない、ビルドも通る、それなのに本番でだけ落ちる——という状況だったため、
最初は原因の見当がつきませんでした。手がかりになったのは、Vercel側が出しているランタイム
ログでした。

## 原因: TypeScriptの型チェックと、実行時のモジュール解決は別物

このプロジェクトでは、以下のような拡張子なしの相対importを書いていました。

```typescript
// server/collect.ts
import { Article } from '../shared/types';
```

TypeScriptの`tsconfig.json`では`moduleResolution: "bundler"`という設定を使っており、
この設定下では拡張子なしの相対importでも型チェックが通ります。ローカルの開発サーバーは
Viteが担っており、Viteは内部でファイルをバンドルする際に、拡張子の省略をよしなに解決して
くれます。つまり**「型チェックが通る」「ローカルのdevサーバーで動く」の両方をクリアして
いても、それは実行時のモジュール解決が正しいことを保証しない**、という状態でした。

一方、Vercel Functionsの実行環境は素のNode.js(ESM)です。Node.jsのESMローダーは、
CommonJSの`require`とは違い、相対importに**拡張子を省略することを許していません**。
`.js`ファイルを読み込むつもりなら、ソースが`.ts`であっても最終的にビルドされる
`.js`という拡張子を明示する必要があります。

つまりこの不具合は、「ビルド・型チェックの担当者(TypeScript + Vite)」と「実際に
コードを実行する担当者(Node.js)」とで、import解決のルールが異なっていたことに
起因していました。ローカルのdevサーバーがVite一色である以上、この差はローカルでは
決して顕在化しません。

## 修正内容

`api/`・`server/`・`shared/`配下の相対importすべてに、`.js`拡張子を明記しました。

```typescript
// 修正後
import { Article } from '../shared/types.js';
```

拡張子が`.ts`ではなく`.js`である点が直感に反するかもしれませんが、これは「TypeScript
のソースファイル名」ではなく「ビルド後に実際に存在するファイル名」を指しているためです。
TypeScriptはこの書き方を、ビルド後の`.js`ファイルへの参照として正しく解釈してくれます。

なお、フロントエンド側(`src/`配下)はViteがビルド・バンドルの両方を担うため、この問題の
対象外です。影響が出るのは、Node.jsが素のESMとして直接実行する`api/`・`server/`配下の
みでした。

## 学んだこと

- **「ローカルで動く」「型チェックが通る」は、本番の実行環境が同じ前提で動いていることを
  保証しない。** 今回はビルドツール(Vite)とランタイム(Node.js)でモジュール解決の
  ルールが異なっていたことが原因でした。開発環境と本番環境の間に、目に見えないレイヤーの
  差がないかを意識するきっかけになりました。
- こうした差分は、ローカルで再現しない以上、実際に本番へデプロイして初めて発覚します。
  今回はVercelのランタイムログを確認したことで、エラーメッセージから直接原因を特定
  できました。ログを丁寧に読むことの重要性を改めて実感しました。
- 再発防止のため、「`api/`・`server/`・`shared/`配下の相対importには`.js`拡張子を
  明記する」というルールをプロジェクトの開発ガイドラインに明文化し、次に同じ構成の
  コードを書くときに迷わないようにしました。
