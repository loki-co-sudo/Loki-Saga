## デプロイして、少し安心していた

個人開発しているニュース収集アプリで、RSSフィードを取得・整形・保存する処理を、
Vercel Functionsという仕組みの上でNode.jsのサーバーサイドコードとして動かして
いました。ローカルの開発サーバーで何度も動作を確認し、型チェックも通り、ビルドも
問題なく成功していたので、デプロイボタンを押したときは「これでもう一区切りだな」
くらいの気持ちでいました。

ところが、実際にデプロイ後の環境で該当の処理を呼び出してみると、こういうエラーで
落ちていました。

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '.../shared/types' imported from '.../server/collect.js'
```

ローカルでは何度動かしても再現しません。ビルドも通っています。型チェックも
通っています。それなのに本番でだけ、しかも毎回確実に落ちる。正直、この時点では
何から疑えばいいのか見当がつきませんでした。

## 手がかりを探す

まず疑ったのは環境変数の設定漏れでした。次に、依存パッケージのバージョン差。
どちらも違いました。ローカルとVercel上のNode.jsのバージョンを揃えてみても
変わりません。「型もビルドも通っているのに、実行時にだけ失敗する」というのは、
今まであまり経験したことのないパターンで、正直かなり戸惑いました。

手がかりになったのは、Vercelが出しているランタイムログでした。エラーメッセージを
そのままよく読み返すと、`ERR_MODULE_NOT_FOUND`というエラーコードと、モジュールを
見つけられなかったファイルパスが書かれています。ここでようやく、「ビルドやテストの
段階では検出できない、実行時特有の何かが起きている」という方向に頭を切り替える
ことができました。

## 何が起きていたのか

このプロジェクトでは、次のような拡張子なしの相対importを書いていました。

```typescript
// server/collect.ts
import { Article } from '../shared/types';
```

普段このコードは、TypeScriptの型チェックも、Viteの開発サーバーでの実行も、
何の問題もなく通っていました。恥ずかしながら、私はこのとき初めて、「型チェックが
通ること」と「実際にそのコードを実行できること」がイコールではない、という
当たり前の事実を、身をもって理解することになりました。

`tsconfig.json`では`moduleResolution: "bundler"`という設定を使っています。この
設定のもとでは、拡張子なしの相対importでも型チェックは通ります。そしてローカルの
開発サーバーはViteが担っていて、Viteは内部でファイルをバンドルする際に、拡張子の
省略をよしなに解決してくれます。つまり「型チェックが通る」も「ローカルのdev
サーバーで動く」も、どちらもVite(とTypeScriptの緩めの設定)がお膳立てしてくれた
上での話であって、実行時のモジュール解決が仕様通りに正しいかどうかとは、実は
何の関係もなかったのです。

一方、Vercel Functionsの実行環境は素のNode.js(ESM)です。Node.jsのESMローダーは、
CommonJSの`require`とは違い、相対importの拡張子省略を許していません。`.js`ファイル
を読み込むつもりなら、たとえソースが`.ts`であっても、最終的にビルドされる`.js`と
いう拡張子を明示する必要があります。

つまりこの不具合は、「ビルド・型チェックを担当するTypeScriptとVite」と「実際に
コードを実行するNode.js」とで、import解決のルールがそもそも違っていたことに
起因していました。ローカルのdevサーバーがVite一色である以上、この差は開発中には
絶対に顕在化しません。本番のNode.js環境に乗せて、初めて表面化する類のズレでした。

## 直した内容

`api/`・`server/`・`shared/`配下の相対importすべてに、`.js`拡張子を明記しました。

```typescript
// 修正後
import { Article } from '../shared/types.js';
```

ソースファイルは`.ts`なのに拡張子が`.js`というのは、最初はどうにも据わりが
悪く感じました。ですがこれは「TypeScriptのソースファイル名」ではなく「ビルド後に
実際に存在するファイル名」を指していると考えると、腑に落ちます。TypeScriptはこの
書き方を、ビルド後の`.js`ファイルへの参照として正しく解釈してくれます。

なお、フロントエンド側(`src/`配下)はViteがビルド・バンドルの両方を担うため、この
問題の対象外です。影響が出るのは、Node.jsが素のESMとして直接実行する`api/`・
`server/`配下のみでした。

## デプロイしてからが本番、という当たり前

この一件があってから、「ローカルで動く」「型チェックが通る」を、本番環境でも
そのまま動く保証だと思い込まないよう、少し慎重になりました。今回はビルドツールと
ランタイムでモジュール解決のルールが異なっていた、という地味な話でしたが、
似たような「開発環境だけが優しくしてくれている」ケースは、探せばまだあるのでは
ないかと思っています。再発防止のために、このルールはプロジェクトの開発ガイド
ラインに明文化しておきました。次に同じ構成のコードを書くときの自分に向けた
メモのつもりです。
